# 자바 개발자를 위한 Node/TypeScript 노트

이 프로젝트를 읽기 전에 알아두면 좋은 것들. 자바와 다른 지점 위주로 정리했다.

## 1. import 에 `.js` 를 붙이는 이유 (제일 헷갈리는 부분)

```ts
import { config } from "../config.js"   // ← 실제 파일은 config.ts 인데 .js 라고 쓴다
```

**오타가 아니다.** TypeScript 는 컴파일 후 `.js` 가 되는데, ESM(ES 모듈) 규격은
import 경로에 확장자를 반드시 요구한다. 그래서 "컴파일 결과 기준"으로 적는다.
`.ts` 라고 쓰면 오히려 에러가 난다.

자바로 치면 `import com.example.Foo` 가 아니라 `import com.example.Foo.class` 를
쓰는 셈이라 어색하지만, Node 진영의 규칙이다.

## 2. 파일 = 모듈. 클래스가 필수가 아니다

자바는 모든 코드가 클래스 안에 있어야 하지만, TS 는 **파일 하나가 모듈**이고
함수를 그냥 최상위에 둘 수 있다.

```ts
export function chunkText(text: string): string[] { ... }   // 클래스 없이 그냥 함수
```

`export` 가 자바의 `public`, 안 붙이면 그 파일 안에서만 쓰는 `private` 이다.

## 3. 최상위 await

```ts
// 파일 맨 바깥에서 바로 await 를 쓴다. main 메서드가 없다.
const collection = await client.getOrCreateCollection({ name: "demo" })
```

자바에는 없는 문법이다. `public static void main` 같은 진입점 없이
파일을 위에서 아래로 실행한다. `examples/` 의 파일들이 전부 이 형태다.

## 4. `Promise<T>` = `CompletableFuture<T>`

```ts
async function generate(texts: string[]): Promise<number[][]> { ... }
const result = await generate(["안녕"])   // await = future.get() 에 가깝다
```

`async` 를 붙이면 반환 타입이 자동으로 `Promise` 로 감싸진다.
자바와 결정적으로 다른 점은 **Node 는 싱글 스레드**라는 것이다.
`await` 는 스레드를 블로킹하지 않고 이벤트 루프에 제어권을 넘긴다.
그래서 `synchronized` 나 락이 거의 필요 없다.

## 5. 타입 시스템이 구조적(structural)이다

자바는 이름이 같아야 같은 타입이다(nominal). TS 는 **모양이 같으면 같은 타입**이다.

```ts
interface Point { x: number; y: number }
const p = { x: 1, y: 2 }    // implements 를 안 썼는데도 Point 로 통한다
```

이게 이 프로젝트에서 실제 버그를 만들었다. `OllamaEmbeddingFunction` 이
chromadb 인터페이스와 모양이 어긋났는데 `implements` 를 안 써서 아무도 못 잡았다.
**그래서 `implements` 를 일부러 붙여뒀다.** 강제는 아니지만 붙이면 검사해준다.

## 6. null 다루기

```ts
a?.b?.c          // Optional chaining — a 가 null 이면 통째로 undefined
x ?? "기본값"     // Nullish coalescing — x 가 null/undefined 일 때만 오른쪽
```

자바의 `Optional.map().orElse()` 를 문법으로 넣은 것이다.
`null` 과 `undefined` 두 가지가 있는데, 실무에서는 거의 구분 없이 쓴다.

## 7. 타입은 런타임에 사라진다

```ts
const body = req.body as SearchRequest     // 캐스팅처럼 보이지만 검사하지 않는다
```

자바 캐스팅은 실패하면 `ClassCastException` 이 난다. TS 의 `as` 는
**컴파일 타임에만 존재**하고 런타임에는 아무 일도 안 한다.
그래서 서버 라우트마다 `if (typeof body.query !== "string")` 같은
수동 검증이 들어가 있다. 스프링의 `@Valid` 가 해주던 일을 직접 해야 한다.

## 8. `import type` 은 타입만 가져온다

```ts
import type { Collection } from "chromadb"   // 런타임 코드로 남지 않음
import { ChromaClient } from "chromadb"      // 실제 값이라 남음
```

인터페이스나 타입은 컴파일하면 사라지므로 `import type` 으로 명시한다.

## 9. 예외에 checked/unchecked 구분이 없다

`throws` 선언이 없고 모든 예외가 unchecked 다. 그래서 어떤 함수가
무엇을 던지는지 시그니처만 봐서는 알 수 없다.
이 프로젝트에서는 `runExample()` 로 한 겹 감싸서 처리한다.

```ts
throw new Error("메시지", { cause: 원인에러 })   // cause 는 자바의 getCause() 와 같다
```

## 10. Express ↔ 스프링 대응

| Express | 스프링 |
|---|---|
| `express()` | `SpringApplication.run()` |
| `Router()` | `@RestController` |
| `router.post("/search", handler)` | `@PostMapping("/search")` |
| `req.body` | `@RequestBody` (단, 검증은 직접) |
| `res.json({...})` | `return ResponseEntity.ok(...)` |
| `app.use(errorHandler)` | `@ControllerAdvice` |
| `app.use(express.json())` | 잭슨 자동 설정 |

가장 큰 차이는 **DI 컨테이너가 없다는 것**이다. `@Autowired` 대신
`import` 로 직접 가져다 쓴다. 싱글턴이 필요하면 모듈 최상위에 `const` 로 만든다.
모듈은 최초 import 시 한 번만 평가되므로 그것이 곧 싱글턴이다.

```ts
export const client = new ChromaClient({ ... })   // @Bean 싱글턴과 같은 효과
```

## 11. `package.json` 의 스크립트

```bash
npm run db      # scripts.db 실행
npm start       # scripts.start (start 는 run 생략 가능)
```

메이븐/그레이들의 `mvn spring-boot:run` 자리다.
`dependencies` 는 런타임, `devDependencies` 는 빌드/테스트용(`<scope>provided</scope>` 느낌).

## 12. `tsx` 가 하는 일

`tsx src/index.ts` 는 컴파일 없이 TS 를 바로 실행한다.
`javac` 없이 `.java` 를 바로 돌리는 셈이다. 타입 검사는 하지 않으므로
따로 `npm run typecheck` (= `tsc --noEmit`) 를 돌려야 한다.

**즉 실행이 된다고 타입이 맞는 건 아니다.** 커밋 전에 typecheck 를 돌리자.
