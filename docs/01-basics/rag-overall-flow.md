# RAG 파이프라인 7단계 흐름 (개발자 관점)

## 1. 실전 7단계 플로우 (온라인 질의 단계)
사용자가 터미널(CLI)이나 채팅창에 질문을 입력했을 때, 뒷단에서 코드가 움직이는 순서다.

1. **질문 접수:** 내 파이썬 스크립트가 사용자의 질문("결제 장애 원인이 뭐야?")을 가로챈다.
2. **질문을 숫자로 변환 (AI 1):** 스크립트가 질문을 **임베딩 모델**에 보내 수백 개의 숫자(벡터)로 변환해 온다.
3. **Vector 창고 검색 (DB 1):** 변환된 숫자 뭉치를 **Vector DB**에 찔러넣어, 뉘앙스가 가장 비슷한 위키 텍스트 조각을 빼온다.
4. **Graph 창고 검색 (DB 2, 그래프를 붙였을 때만):** **Graph DB**에서 질문과 얽힌 인물/문서 팩트 관계망을 빼온다. 진입점을 잡는 방식은 두 갈래다 — 3단계 벡터 검색 결과를 **진입 노드로 넘겨받아 확장**하거나, 질문에서 뽑은 키워드로 **독립적으로 검색한 뒤 결과를 융합**하거나. 어느 쪽이 표준인지는 정해져 있지 않다 (상세는 [rag-graphdb-hybrid-pipeline.md](../03-graphrag/rag-graphdb-hybrid-pipeline.md) 4장).
5. **프롬프트 조립:** 내 스크립트가 찾아온 텍스트 조각과 팩트 관계망을 모아 하나의 거대한 텍스트(프롬프트 밥상)로 조립한다.
6. **답안지 작성 (AI 2):** 조립된 프롬프트를 인터넷을 통해 **LLM(클로드/제미나이 API)**에 전송하여 답변 생성을 요청한다.
7. **최종 출력:** LLM이 요약해 준 최종 답변 글을 내 스크립트가 화면에 출력한다.

*요약:* 결국 RAG 개발이란, 가운데 서서 이쪽저쪽(임베딩 ➡️ DB ➡️ 제미나이)으로 쉴 새 없이 데이터를 실어 나르는 **지휘자 스크립트(택배 기사)**를 짜는 일이다.

## 2. 임베딩 모델(AI 1)은 어디에 있는가?
임베딩 모델은 글의 의미를 파악해 숫자로 바꿔주는 훌륭한 AI다. 이 AI는 내 코드에 내장되어 있을까? 개발자의 상황에 따라 두 가지 방식 중 하나를 선택한다.

**방식 A. 외부 API 호출 (가장 흔함)**
- 클로드나 제미나이를 쓸 때처럼, OpenAI나 Upstage 같은 회사의 **임베딩 전용 API**(예: `text-embedding-3-small` / `text-embedding-3-large`)를 인터넷으로 호출하는 방식. — **모델명에 `-small`/`-large` 접미사까지가 정식 이름이다.** `text-embedding-3`이라는 모델은 없고, 둘은 기본 차원 수가 다르다(1536 vs 3072).
- 스크립트는 가볍지만, 문서를 숫자로 바꿀 때마다 소정의 API 요금이 발생한다.
- **사내 문서를 외부로 내보내도 되는가**가 성능보다 먼저 걸리는 조건이다. 이건 기술 선택이 아니라 정책 문제다.

**방식 B. 로컬 모델 내장 (오픈소스)**
- HuggingFace 등에 공개된 가벼운 임베딩 모델(예: `all-MiniLM-L6-v2`)을 내 컴퓨터에 직접 다운로드받아 파이썬 스크립트 안에 통째로 내장시켜 구동하는 방식.
- 인터넷 연결이 필요 없어 문서가 외부로 나가지 않는 게 최대 이점이다. 대신 내 컴퓨터의 CPU/GPU 자원을 꽤 잡아먹고, 관련 라이브러리(PyTorch 등) 때문에 파이썬 프로젝트 용량이 커진다.
- ⚠️ **"무료"는 모델 라이선스에 달렸다.** HuggingFace에는 상업 이용을 금지하는 라이선스(CC-BY-NC 등)로 배포되는 모델이 섞여 있다. `all-MiniLM-L6-v2`는 Apache-2.0이라 문제없지만, **오픈소스 = 무조건 상업 이용 가능이 아니다.** 사내 도입 전에 모델 카드의 라이선스를 반드시 확인한다.

## 3. 핵심 오해: LLM 내부에는 RAG나 DB가 없다
초보자들이 가장 많이 하는 오해는 "제미나이나 챗GPT(LLM)가 자체적으로 내 문서를 검색해 주고 DB를 돌린다"고 착각하는 것이다.

- **LLM은 껍데기가 아니라 알맹이다:** LLM(API) 내부에는 RAG 파이프라인도, DB 창고도 전혀 없다. 오로지 프롬프트를 읽고 텍스트를 생성하는 뇌세포(가중치 신경망)만 덩그러니 있을 뿐이다.
- **RAG는 껍데기 프로그램이 돌린다:** 사용자의 질문을 보고 *"어? 이건 검색이 필요하네"*라고 판단해서 벡터 DB 창고를 뒤지는 것은, LLM을 바깥에서 감싸고 있는 **'껍데기 프로그램(챗봇 웹사이트나 내가 짠 파이썬 스크립트)'**이다. 껍데기(파이썬)가 창고를 털어서 알맹이(LLM)에게 떠먹여 주는 구조다.
- **상용 챗봇도 껍데기 쪽에 검색을 달아 쓴다:** 챗GPT의 파일 업로드나 웹 검색 기능도 모델 가중치가 하는 일이 아니라 **그 껍데기가 검색해서 프롬프트에 실어주는 것**이다. 구조는 내가 짜는 것과 같고, 규모와 완성도만 다르다.
- 🔍 **그래프 DB가 상용 챗봇에 들어있는지는 확인할 수 없다:** 상용 서비스의 내부 구현은 비공개다. *"챗GPT에는 그래프 DB가 없다"*고 단정할 근거는 없고, 다만 **일반 사용자용 범용 챗봇에 사내 지식 그래프가 있을 이유가 없다**는 게 합리적 추론이다. 확실한 건 하나 — **내 사내 데이터를 대상으로 한 그래프는 내가 직접 구축해야 한다.** 남이 만들어줄 수 있는 물건이 아니다.

## 4. 핵심 오해 2: RAG는 압축이 아니라 선별이다 (★)

*"문서를 잘게 잘라서 토큰을 줄여 LLM에 넣는 것"*이라는 이해는 방향이 반대다. **토큰이 적어지는 건 결과지 목적이 아니다.**

- **압축(요약)** — 정보량 자체를 줄인다. 원본은 버려진다.
- **RAG** — 원본을 **전부** 저장해둔 채, 질문이 올 때 **필요한 조각만 고른다**. 버리는 게 아니라 안 꺼내는 것이다.

**증거는 청킹 안에 이미 있다.** 조각을 10~20% 겹치게 자르면(오버랩) 저장되는 텍스트 총량이 원본보다 **늘어난다**. 압축이라면 늘어날 수가 없다. 상세는 [rag-pipeline.md](../02-pipeline/rag-pipeline.md) 3-3.

**왜 요약본을 안 넣고 원문 조각을 넣나.** 요약을 태우면 `"연차는 익년 3월 31일까지 이월"` 같은 **구체 수치와 조항 문구가 날아간다.** RAG가 답해야 하는 게 대개 바로 그 수치라서, 요약본은 근거로 쓸 수가 없다. (**기본형 기준.** 요약을 인덱스로 함께 쓰는 변형도 존재한다 — RAPTOR 등, **세부는 확인 안 됨**)

### 4-1. 깔때기 — 토큰이 줄어드는 지점은 한 곳뿐

```
원본 문서 10,000페이지         ≈ 수백만 토큰   ← 전부 저장한다. 안 줄인다
   │  파싱          (포맷 변환)
   │  청킹          (분할)     → 조각 수만 개  ← 오버랩 때문에 총량은 오히려 증가
   │  임베딩·색인   (저장)
   ▼
질문 도착
   │  검색  ← ★ 벡터DB / 그래프DB / BM25가 사는 칸
   ▼                           → 후보 수십 개
   │  리랭킹                   → 5~10개
   ▼
프롬프트 조립                   수천 토큰      ← 토큰이 줄어드는 지점은 여기 하나뿐
```

⚠️ **숫자는 감을 잡기 위한 어림값이고 정해진 값이 아니다.** 페이지당 토큰 수는 언어·조판에 따라 크게 달라지고, 후보 개수와 최종 5~10개도 **흔한 관행일 뿐 규칙이 아니다.**

**핵심.** 파싱·청킹·임베딩·벡터DB·그래프DB **어느 것도 프롬프트 토큰을 줄이지 않는다.** 전부 마지막에 실을 5~10개를 **정확하게 고르기 위한 준비 작업**이다. 이 다섯을 아무리 잘 해도 프롬프트 토큰은 1토큰도 안 줄고, 대신 **고른 조각이 정답을 담고 있을 확률**이 오른다. 그게 전부다.

**파싱과 청킹의 경계도 여기서 갈린다.**

- **파싱** — 포맷 변환. PDF 바이너리 → 텍스트 + 구조 정보.
- **청킹** — 분할. 그 텍스트를 검색 단위로 자른다. 포맷은 안 건드린다.

순서를 뒤집을 수 없는 이유가 여기 있다. 파싱이 제목 계층을 못 뽑으면 **구조 기준 청킹이 애초에 불가능**하다 ([rag-pipeline.md](../02-pipeline/rag-pipeline.md) 3-2).

⚠️ 단, 이건 **역할 구분**이지 도구 경계가 아니다. 실제 레이아웃 파서 계열은 출력이 이미 요소(element) 단위로 쪼개져 나와서 **구현상 두 단계의 경계가 흐릿한 경우가 있다.**

### 4-2. 벡터DB와 그래프DB는 같은 칸에 있다

둘을 별개 층위로 놓으면 혼란이 온다. **상하 관계가 아니라 담당하는 질문 종류가 다를 뿐**, 위 깔때기의 **같은 칸(후보 뽑기)** 안에 나란히 있다.

- **벡터DB** — *"뜻이 비슷한 문단 찾아와."* 표현이 달라도 의미가 가까우면 걸린다. 대신 정확한 문자열과 다단계 관계에 약하다 ([vector-db.md](../01-basics/vector-db.md) 5장).
- **그래프DB** — *"A와 얽힌 것들, 몇 다리 건너까지 따라와."* 여러 문서에 걸쳐 흩어진 관계를 따라간다 ([rag-graphdb-hybrid-pipeline.md](../03-graphrag/rag-graphdb-hybrid-pipeline.md) 2장).

**하이브리드 구성에서는 그래프를 붙였다고 벡터 검색이 빠지지 않는다.** 둘 다 후보를 뱉고, 지휘자 스크립트가 합쳐서 리랭킹에 넘긴다. 위 1장의 **3단계와 4단계가 정확히 이 칸**이다.

### 4-3. 진짜 '압축'에 해당하는 단계는 따로 있다

검색으로 조각 5~10개를 건져도, **그 조각 안에 질문과 무관한 문장이 섞여 있다.** 이걸 질문 기준으로 잘라내 프롬프트를 실제로 줄이는 기법이 따로 존재한다.

- 기준은 **문서 구조가 아니라 질문**이다. 같은 조각이라도 질문이 바뀌면 남는 문장이 달라진다.
- 그래서 **색인 시점이 아니라 질의 시점**에 돈다. 파싱·청킹이 오프라인 작업인 것과 층위가 다르다.
- LangChain 계열에서 **contextual compression**이라는 이름으로 부른다 (**이름은 거의 확실, 정확한 클래스명·구현 세부는 확인 안 됨**).

즉 "압축"은 RAG에 없는 개념이 아니라, **파싱·청킹이 아니라 검색 이후에 붙는 별개 단계**다. 이 자리를 헷갈리면 청킹을 압축으로 오해하게 된다.

---

📌 **핵심 요약**
RAG의 주체는 LLM이 아니라 **내가 짠 지휘자 스크립트**다. 스크립트가 임베딩 모델(AI 1)로 질문을 벡터화하고, 벡터 DB(+그래프 DB)에서 근거를 긁어와, 프롬프트로 조립해 LLM(AI 2)에 넘긴다. LLM 내부에는 검색도 DB도 없고 프롬프트를 읽어 텍스트를 뽑는 가중치만 있다. 임베딩 모델은 외부 API냐 로컬 내장이냐로 갈리며, 그 선택은 성능보다 **보안 정책과 라이선스**가 먼저 결정한다. 그리고 이 파이프라인은 문서를 **압축하는** 게 아니라 **선별하는** 장치다 — 파싱·청킹·임베딩·DB는 토큰을 줄이지 않고, 마지막에 실을 5~10개를 정확히 고르기 위해 존재한다.

🔗 **참고 자료**
- LangChain Framework (파이썬 지휘자 코드를 단 몇 줄로 짜게 해주는 라이브러리)

🌱 **심화 키워드**
- **Local LLM / Local Embedding:** 외부 API에 의존하지 않고 온프레미스(사내 서버나 내 PC)에서 직접 AI 모델을 구동하여 보안을 극대화하는 방식.
- **LangChain / LlamaIndex:** 위 7단계의 복잡한 파이프라인과 API 호출을 손쉽게 연결(Chain)해 주는 RAG 특화 프레임워크.
- **Contextual Compression:** 검색해서 건진 조각 안에서 **질문과 무관한 문장만 잘라내** 프롬프트를 줄이는 질의 시점 기법 (4-3장).
- **RAPTOR:** 원문 조각과 요약을 계층으로 함께 인덱싱하는 변형. "요약은 근거로 못 쓴다"는 기본형의 예외가 어디까지인지 볼 수 있는 사례.
