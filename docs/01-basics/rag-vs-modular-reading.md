# RAG 도입 기준과 모듈형 지식 주입

> 학습 위치: [전체 문서 지도](../README.md) · 다음: [RAG 전체 흐름](../01-basics/rag-overall-flow.md)

> 모든 AI 시스템에 무조건 RAG(벡터 DB)가 필요한 것은 아니다. 데이터의 규모와 성격에 따라 '검색'을 쓸지, '직접 읽기'를 쓸지 아키텍처를 결정해야 한다.

> 관련 문서:
> - [rag-overall-flow.md](../01-basics/rag-overall-flow.md) — RAG를 쓰기로 했을 때의 실행 순서
> - [rag-practical-implementation.md](../02-pipeline/rag-practical-implementation.md) — 실제 구축 스택과 청킹 전략

> **확신도 표기 원칙** — 아키텍처 판단 기준은 확실, **상용 챗봇(챗GPT·클로드)의 대화 기억 구현은 비공개라 추측**으로 표기한다.

## 1. RAG(벡터 DB)가 반드시 필요한 경우
- **조건:** 사내 위키, 수만 건의 슬랙 대화 기록 등 **데이터가 방대하고 불규칙할 때.**
- **이유:** LLM이 한 번에 읽을 수 있는 뇌 용량(토큰 컨텍스트 한도)에는 제한이 있다. 한도 내라 하더라도 글이 길어질수록 API 비용이 폭발하며, 중간 내용을 까먹는 현상(Lost in the Middle)이 발생한다.
- **해결:** 따라서 전체 데이터를 잘게 쪼개어 벡터 DB에 넣고, 질문과 관련된 3~5개의 텍스트 조각만 **'검색'**해서 프롬프트에 끼워 넣는 RAG 파이프라인이 필수적이다.

## 2. RAG가 오버스펙인 경우: 모듈형 지식 주입 (에이전트 직접 읽기)
- **조건:** 채점 봇(면접관 에이전트)이나 특정 가이드 봇처럼 규칙 문서가 수십 장 내외로 제한적이고, **'어느 단계에서 어떤 문서를 봐야 할지' 프로세스가 명확할 때.**
- **해결:** 굳이 복잡한 파이썬 스크립트와 벡터 DB 서버를 세팅할 필요가 없다. 대신 지식 문서들을 역할에 따라 여러 파일로 쪼개어 폴더에 둔다(`levels.md`, `rubric.md` 등). 그리고 LLM(에이전트)에게 *"1단계 평가할 때는 levels 파일을 열어서 읽고, 3단계 채점할 때는 rubric 파일을 열어서 읽어라"*라고 지시한다.
- **장점:** 벡터 검색의 고질적 단점인 '검색 실패(엉뚱한 조각을 가져올 위험)' 없이 100% 확정적인 지식을 필요한 타이밍에만 주입할 수 있으며, 시스템 구조가 압도적으로 가볍다.

## 3. 웹 챗봇(클로드/제미나이)의 '대화 기억' 원리
채팅 앱에서 이전 대화 내용을 기억하고 이어가는 것은 RAG(벡터 검색)일까? **기본적으로는 RAG가 아니다.**

- **통째로 욱여넣기 (Prompt Stuffing):** 우리가 "안녕" ➡️ "반가워" ➡️ "내 이름은 철수야" 라고 채팅을 칠 때마다, 앱은 뒤에서 몰래 **이전까지 나눈 모든 대화 기록을 하나의 거대한 텍스트로 묶어서** API에 매번 다시 전송한다. LLM은 사람처럼 기억력이 있는 게 아니라, 메시지를 보낼 때마다 '지금까지의 톡방 전체 캡처본'을 건네받고 처음부터 다 읽은 뒤 대답하는 것이다. 문서가 적을 때 쓰는 무식하지만 가장 확실한 방법이다.
- **RAG가 개입할 만한 예외 상황:** 대화가 너무 길어져 컨텍스트 윈도우를 초과하거나, ChatGPT의 'Memory(기억)' 기능처럼 몇 달 전 대화를 장기 기억해야 할 때는 캡처본 통째 전송이 불가능해진다. 이때는 과거 대화를 잘라 저장해두고 **필요한 조각만 검색해 현재 대화에 끼워 넣는** 방식이 자연스러운 해법이다.
  - 🔍 **다만 상용 서비스가 실제로 벡터 DB + RAG로 구현했는지는 확인할 수 없다** (내부 구현 비공개). 요약 압축, 구조화된 프로필 저장, 키워드 검색 등 다른 수단도 가능하다. **"이렇게 풀 수 있다"는 구조적 추론이지 "이렇게 되어 있다"는 사실이 아니다.**

**정리하면 대화 기억의 기본값은 RAG가 아니라 통째로 다시 보내기(Prompt Stuffing)다.** 검색이 끼어드는 건 그게 물리적으로 불가능해지는 지점부터다 — 여기서도 판단 기준은 1·2장과 같다. **"미리 무엇을 봐야 할지 정할 수 있는가."**

---

📌 **핵심 요약**
RAG는 기본값이 아니라 **선택지 중 하나**다. 데이터가 방대하고 어느 문서를 볼지 미리 못 정할 때만 값을 한다. 규칙 문서가 수십 장이고 단계별로 읽을 파일이 정해져 있다면 **에이전트에게 파일을 직접 읽히는 모듈형 주입**이 더 정확하고(검색 실패가 없다) 더 가볍다. 웹 챗봇의 대화 기억도 기본은 검색이 아니라 이전 대화 전체를 매번 다시 보내는 Prompt Stuffing이다. 판단 기준은 규모가 아니라 **"볼 문서를 미리 확정할 수 있는가"**다.

🌱 **심화 키워드**
- **Lost in the Middle:** 프롬프트에 참조할 문서를 너무 많이 밀어 넣으면, LLM이 처음과 끝부분만 기억하고 중간에 끼어있는 핵심 팩트를 무시하거나 놓치는 치명적인 현상.
- **Agentic RAG (에이전트 RAG):** 단순한 벡터 검색을 넘어, AI가 스스로 판단하여 "아, 이 질문은 사내 문서를 검색(RAG)해야겠다", "이 질문은 그냥 웹 검색을 해야겠다"라며 도구를 자율적으로 선택하는 고도화된 아키텍처.
