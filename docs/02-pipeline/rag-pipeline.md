## 1. 왜 RAG가 필요한가 — 전부 넣으면 안 되는 네 가지 이유

사내 문서 2만 건에 근거해서 답하는 시스템을 만든다고 하자. 가장 단순한 발상은 **문서를 전부 프롬프트에 넣는 것**이다. 이게 안 되는 이유가 곧 RAG의 존재 이유다.

**어림 계산 (전제: 문서 한 건 10페이지 약 5,000토큰)** — 2만 건이면 약 **1억 토큰**. 문서 두께 가정에 따라 크게 흔들리므로 자릿수 감각으로만 쓴다.

- **컨텍스트 윈도우.** 큰 축의 모델이 100만 토큰대다 (**2026년 8월 기준 어림이고, 더 큰 윈도우를 표방하는 모델도 있다. 수치는 빨리 낡는다**). 1억 토큰은 그 100배라 애초에 안 들어간다. **자릿수 격차라는 점이 요지이므로 윈도우가 몇 배 커져도 결론은 안 바뀐다.**
- **비용.** LLM은 입력 토큰에도 과금한다. **질문 한 건마다 전체 DB를 풀스캔해서 네트워크로 전송하는 것**과 같다. 정확한 단가는 모델마다 다르고 자주 바뀌므로 여기 적지 않는다.
- **지연.** 답을 쓰기 전에 입력 전체를 읽는 단계(prefill)가 있고 입력 길이에 비례한다.
- **품질 저하.** 앞의 셋이 전부 해결돼도 남는다. **긴 입력의 중간에 놓인 정보를 모델이 잘 못 꺼내 쓴다.** 앞과 뒤는 보는데 가운데가 흐려진다. (Liu 외 "Lost in the Middle", 2023 — 논문 존재와 결론 방향은 거의 확실, 세부 실험 조건은 **미확인**)

**그래서 결론이 뒤집힌다.** 적게 넣는 건 어쩔 수 없이 하는 타협이 아니라 **잘하려면 반드시 해야 하는 일**이다.

> **함께 알아둘 것 — LLM은 stateless다.** 매 호출이 완전히 독립적이고 세션도 이전 대화 기억도 없다. 우리가 넣어준 프롬프트 텍스트가 **그 호출에서 모델이 아는 세상의 전부**다. 대화가 이어지는 것처럼 보이는 챗봇도 매번 이전 대화 전체를 다시 실어 보내는 것뿐이다.

> **비용과 지연은 프롬프트 캐싱으로 일부 깎을 수 있다.** 다만 캐싱은 윈도우 한계를 못 넘고, 앞부분이 바뀌면 무효화된다. **캐시 무효화 문제가 여기서도 그대로 나온다.**

## 2. 전체 골격 — 파이프라인은 두 개다

성격이 완전히 다른 파이프라인 두 개가 벡터DB를 사이에 두고 붙어 있다.

```
[오프라인 - 인덱싱]  문서가 들어올 때 한 번, 배치로 돈다
  원본 문서
    → 파싱      바이너리에서 텍스트와 구조를 뽑는다
    → 청킹      검색 단위로 자른다
    → 임베딩    각 조각을 벡터로 바꾼다 (호출당 비용 발생)
    → 저장      벡터DB에 조각 + 벡터 + 메타데이터를 넣는다
                          │
                       [벡터DB]
                          │
[온라인 - 질의]  질문 하나마다 매번 돈다, 지연이 곧 UX다
  질문
    → 질의 변환   질문을 검색에 맞게 다듬는다 (선택)
    → 검색        벡터 검색과 키워드 검색으로 후보 수십 개
    → 리랭킹      후보를 다시 정렬해 상위 몇 개만 남긴다
    → 프롬프트 조립  고른 조각을 질문과 함께 하나의 텍스트로 만든다
    → LLM 호출    답변 생성
    → 후처리      출처 붙이기, 근거 검증
```

**백엔드 감각으로 옮기면** 위쪽은 ETL 배치 잡이고 아래쪽은 조회 API다. 그리고 둘의 관계는 **캐시와 원본의 관계**와 같다. 원본이 바뀌었는데 파생 데이터가 안 바뀌면 오래된 답이 나간다. **RAG의 최신성 문제는 새로운 문제가 아니라 캐시 무효화 문제다.**

이름의 유래도 여기서 나온다.

- **R (Retrieval)** — 검색해서 조각을 찾는 단계
- **A (Augmented)** — 그 조각을 프롬프트에 끼워 넣어 질문을 보강하는 단계
- **G (Generation)** — LLM이 그걸 읽고 답을 쓰는 단계

## 3. 오프라인 파이프라인

추적 예제를 고정한다. 문서는 `인사규정_2026개정.pdf`(50페이지, 표 포함), 질문은 `"작년에 못 쓴 연차 이월되나요?"`.

### 3-1. 파싱 (Parsing)

**입력** PDF 바이너리 → **출력** 텍스트와 구조 정보(제목 계층, 표, 페이지 번호)

**PDF는 인쇄용 포맷이지 데이터 포맷이 아니다.** 내부적으로 "이 좌표에 이 글자를 찍어라"의 나열이라, 문단 경계나 제목 여부에 대한 정보가 없거나 부실하다.

- **2단 조판**을 순진하게 읽으면 좌우 단이 한 줄씩 번갈아 섞인다
- **표**를 텍스트로 뽑으면 행과 열 구조가 무너져 숫자만 남는다
- **머리말과 꼬리말**이 페이지마다 본문에 끼어든다
- **스캔 PDF**는 이미지라 OCR을 태워야 하고 오탈자가 섞인다

스키마 없는 레거시에서 데이터를 긁어오는 ETL 추출 단계와 같다. **여기서 깨진 데이터는 하류에서 복구되지 않는다.**

### 3-2. 청킹 (Chunking)

**입력** 문서 전체 텍스트 → **출력** 조각 수십에서 수백 개

**청킹은 검색 인덱스의 입도(granularity)를 정하는 작업**이다. RDB에서 거대한 TEXT 컬럼 하나를 LIKE로 긁는 것과, 정규화해서 행 단위로 쪼개고 인덱스를 거는 것의 차이와 같다.

**핵심 트레이드오프** — 양쪽 다 문제가 있다.

|               | 크게 자른다                                                                                                             | 작게 자른다                                  |
| ------------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| 검색 선택도   | **나쁘다.** 한 조각에 여러 주제가 섞이면 어느 주제로도 선명하게 안 걸린다. 컬럼 다섯 개를 이어붙여 인덱스를 건 꼴 | 좋다                                         |
| 문맥 보존     | 좋다                                                                                                                    | **나쁘다.** 조각 혼자서는 말이 안 된다 |
| 프롬프트 부담 | 크다                                                                                                                    | 작다                                         |

**작게 자를 때 실제로 아픈 건 "답이 걸쳐서 못 찾는 것"보다 "걸렸는데 의미를 모르는 것"이다.**

- `"위 조항에 해당하는 경우 30일 이내에 신청해야 한다"` — 위 조항이 뭔지 이 조각엔 없다
- 표가 잘려서 헤더는 앞 조각, 숫자는 뒷 조각에 있다. 뒷 조각만 걸리면 숫자만 있고 뜻을 모른다
- 조각에 이게 2023년판인지 2026년 개정본인지가 안 적혀 있다. 원문에는 표지에만 있었으니까

**전략 종류.**

- **고정 크기** — N자마다 자른다. 구현이 쉽고 문장 중간에서 잘린다
- **구분자 기준** — 문단이나 문장 단위로 자르고 크기 상한을 둔다. 실무 기본값에 가깝다
- **구조 기준** — 파싱에서 얻은 제목 계층으로 섹션 단위로 자른다. **파싱이 잘 됐을 때만 가능하다**
- **의미 기준(semantic)** — 인접 문장 임베딩을 비교해 의미가 바뀌는 지점에서 자른다. 색인 비용이 오르고 **효과는 문서 성격에 따라 들쭉날쭉하다.** 항상 낫다는 보장은 없다 (추측 섞임)

### 3-3. 오버랩 — 완화이지 해결이 아니다

조각 경계에 답이 걸리는 문제의 가장 단순한 대응은 **겹치게 자르는 것**이다.

```
0 ~ 1000     조각 1
800 ~ 1800   조각 2   (앞 200자를 조각 1과 공유)
1600 ~ 2600  조각 3   (앞 200자를 조각 2와 공유)
```

조각 크기의 10에서 20퍼센트 정도를 겹치는 게 흔한 관행이다. (**관행이고 정해진 법칙이 아니다**)

**대가가 세 겹으로 청구된다.**

- **저장 비용** — 조각 수가 늘고 벡터DB 용량도 비례해서 는다
- **임베딩 비용** — 조각마다 임베딩을 태우니 초기 색인 비용이 그대로 는다
- **검색 결과 오염** — 겹친 부분이 걸리면 **거의 같은 내용의 조각이 상위에 나란히 올라온다.** 프롬프트에 실을 자리 다섯 칸 중 셋을 낭비하게 된다

**한계.** 잘린 논리가 오버랩 폭보다 길면 여전히 깨진다. 오버랩을 키워서 문맥 문제를 다 막으려는 시도는 실패한다. 비용만 폭발하고 중복 오염이 심해진다.

### 3-4. 검색 단위와 투입 단위를 분리한다 (★)

**"검색해서 걸린 조각을 그대로 LLM에 넣는다"는 전제를 깨면** 위 딜레마의 출구가 생긴다. 이게 이 주제에서 가장 중요한 발상 전환이다.

- **작게 검색하고 크게 넣는다.** 검색은 작은 조각으로 해서 선택도를 살리고, LLM에 실을 때는 그 조각이 속한 **부모 덩어리**(문단, 섹션, 앞뒤 조각)를 꺼내 넣는다. **인덱스로 행을 찾은 뒤 실제로는 조인해서 붙인 결과를 반환하는 것**과 같은 구조다. parent document retrieval 또는 small-to-big이라고 부른다
- **조각에 맥락을 미리 심어둔다.** 색인 시점에 각 조각 앞에 "이 문서는 2026년 개정 인사규정이고 이 조각은 연차 항목에 속한다" 같은 요약을 붙여 저장한다. 조각 혼자서도 말이 되고 검색에도 그 맥락이 반영된다. Anthropic이 contextual retrieval이라는 이름으로 정리해 공개했다 (**방식은 거의 확실, 제시된 개선 수치와 정확한 URL은 미확인**)

**대가.** 앞의 것은 저장 구조가 복잡해지고(조각과 부모의 관계 관리), 뒤의 것은 **색인 때 조각마다 LLM을 한 번씩 태워야 해서** 초기 비용이 크게 오른다.

### 3-5. 메타데이터 — 여기서 안 심으면 나중에 못 만든다 (★)

조각 텍스트만 저장하면 안 된다.

#### 육하원칙으로 먼저 보기

| 질문                       | 답                                                                                                                                                         |
| :------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **누가 만드는가?**   | 개발자가 필드와 규칙을 설계하고, 실행할 때 API 호출자·문서 수집기·파서·청킹 코드가 값을 제공한다. 최종 메타데이터 객체는 적재 코드가 청크별로 조립한다. |
| **언제 만드는가?**   | 문서를 입력받을 때부터 값을 모으고, 파싱·청킹을 마친 뒤 벡터DB에 적재하기 직전에 청크별 최종 형태를 완성한다.                                             |
| **어디서 만드는가?** | 문서 인제스트(적재) 파이프라인에서 만든다. 현재 프로젝트에서는[`ingestDocument()`](../../src/lib/documents.ts)가 공통 값과 시스템 값을 병합한다.             |
| **무엇을 넣는가?**   | 출처·제목·페이지·섹션, 분류·연도, 접근 권한, 문서 ID·버전, 청크 순번·부모 ID처럼 나중에 필터링·표시·관리할 값을 넣는다.                            |
| **어떻게 만드는가?** | 문서 공통 값은 모든 청크에 상속하고, 파서·청커가 만든 위치별 값과 적재 코드가 만든 시스템 값을 합쳐`documents`와 함께 `metadatas`로 저장한다.         |
| **왜 만드는가?**     | 검색 범위 필터링, 출처 표시, 접근 권한 검사, 문서 갱신·삭제, 청크와 원문의 연결을 가능하게 하기 위해서다.                                                 |

한 문장으로 줄이면, **개발자가 미리 정한 규칙에 따라 적재 프로그램이 파싱·청킹 결과와 문서 정보를 합쳐 청크별 메타데이터를 만들고, 검색과 문서 관리를 위해 벡터DB에 본문과 함께 저장한다.**

```json
{
  "text": "제23조(연차휴가) ... 미사용 연차는 익년도로 이월하지 아니한다 ...",
  "doc_id": "hr-policy-2026",
  "doc_title": "인사규정 2026 개정",
  "section": "제5장 휴가 > 제23조 연차휴가",
  "page": 18,
  "version": "2026-01-01",
  "acl": ["employee"],
  "updated_at": "2026-01-01"
}
```

**이 메타데이터가 실패 모드 2번, 3번, 4번의 방어선 전체다.**

- `version`이 없으면 2023년판과 2026년판을 구분할 수 없다
- `acl`이 없으면 권한 필터를 걸 수단 자체가 없다
- `doc_id`가 없으면 문서 수정 시 기존 조각을 묶어서 지울 수가 없다

#### 무엇을 넣을지는 누가 정하는가

메타데이터의 스키마는 **애플리케이션 개발자가 정한다.** 임베딩 모델이나 벡터DB가 문서의 제목·권한·버전을 알아서 만들어주지 않는다. 기준은 단순하다. **나중에 무엇으로 필터링하고, 출처를 표시하고, 갱신·삭제할 것인가**를 먼저 정한 뒤 그 작업에 필요한 필드를 넣는다.

| 목적           | 필드 예시                                                 |
| :------------- | :-------------------------------------------------------- |
| 출처 표시      | `source`, `doc_title`, `page`, `section`          |
| 검색 범위 제한 | `category`, `year`, `department`, `document_type` |
| 접근 제어      | `tenant_id`, `access_level`, `acl`                  |
| 갱신·삭제     | `doc_id`, `version`, `updated_at`                   |
| 청크 추적      | `chunk_idx`, `parent_id`, `heading`                 |

필드 이름을 자유롭게 정할 수는 있지만, 문서마다 `year`와 `publishedYear`를 섞어 쓰는 식으로 스키마가 흔들리면 필터가 누락된다. 타입도 `year: 2026`과 `year: "2026"`을 섞지 않는다. 또한 벡터DB 제품이 허용하는 메타데이터 값의 타입이 다를 수 있으므로, 실제 저장 전에 사용하는 클라이언트의 제약을 확인하고 검증해야 한다.

#### 언제 넣는가

메타데이터는 **파싱·청킹을 마친 뒤, 청크를 벡터DB에 적재하기 직전** 완성한다.

```text
문서 입력
  ↓ 문서 공통 메타데이터 확보
파싱
  ↓ 페이지·제목·표 같은 구조 정보 추출
청킹
  ↓ 청크 순번·부모 ID 같은 청크 정보 생성
메타데이터 병합  ← 이 시점에 청크별 최종 형태 완성
  ↓
임베딩 + 벡터DB 적재
```

정보의 출처에 따라 만들어지는 시점이 다르다.

- **문서 입력 시점** — 제목, 부서, 작성일, 문서 유형, 접근 등급
- **파싱 시점** — 페이지 번호, 마크다운 제목, 표 여부
- **청킹 시점** — 청크 순번, 부모 청크 ID, 섹션 경로
- **적재 시점** — 문서 ID, 적재 시각, 버전처럼 시스템이 관리하는 값

문서 공통 값은 모든 청크가 물려받고, `page`·`heading`·`chunk_idx`처럼 위치에 따라 달라지는 값은 청크별로 덧붙인다.

#### 실제로 누가 만드는가

“적재 직전에 메타데이터를 넣는다”는 말은 **사람이 문서의 청크마다 값을 수동으로 작성한다는 뜻이 아니다.** 개발자가 메타데이터의 필드와 생성 규칙을 코드로 한 번 정의해두면, 문서 적재 파이프라인이 실행될 때 그 규칙에 따라 청크별 객체를 자동으로 만든다.

여기서는 서로 다른 세 역할을 분리해야 한다.

| 역할                                   | 담당 주체                                  |
| :------------------------------------- | :----------------------------------------- |
| 어떤 메타데이터 필드를 사용할지 설계   | 개발자·서비스 설계자                      |
| 각 필드의 실제 값을 제공하거나 추출    | 파일, 업무 시스템, 파서, 규칙 코드 또는 AI |
| 여러 값을 최종 객체로 조립해 DB에 전달 | 인제스트 코드                              |

즉 **메타데이터 객체를 만드는 주체는 인제스트 프로그램**이고, 객체 안에 들어가는 **값의 생산자는 필드마다 다르다.** “누가 만드는가?”에 하나의 답만 붙이려고 하면 이 둘이 섞여 혼란이 생긴다.

```text
개발자
  └─ 필드와 생성 규칙을 미리 구현
       ↓ 실행 시
API 호출자·문서 수집기 ── 문서 공통 정보 제공
파서                  ── 페이지·제목 등 추출
청킹 코드             ── 청크 순번·부모 ID 생성
적재 코드             ── 위 값을 청크별로 병합
       ↓
벡터DB에 본문 + 메타데이터 저장
```

값마다 실제 생성 주체가 다르다.

| 필드 예시                            | 값을 만드는 주체                      | AI 필요 여부              |
| :----------------------------------- | :------------------------------------ | :------------------------ |
| `source`, 원본 URL                 | 파일 업로더·문서 수집기              | 불필요                    |
| `page`, `heading`                | PDF·마크다운 파서                    | 불필요                    |
| `chunkIdx`, `parentId`           | 청킹 코드                             | 불필요                    |
| `ingestedAt`, 내부 문서 ID         | 적재 코드                             | 불필요                    |
| `accessLevel`, `tenantId`        | 권한·문서 관리 시스템                | AI 사용 금지              |
| `category`                         | 문서 관리 시스템, 규칙 또는 AI 분류기 | 상황에 따라 필요          |
| `summary`, `topic`, `keywords` | 본문을 읽는 LLM·분류 모델            | 의미 추론이 필요하면 사용 |
| `entities`                         | 개체명 인식기 또는 LLM                | 대체로 AI·NLP 사용       |

#### 메타데이터 생성과 AI의 관계

원본이 문장뿐이고 그 의미를 읽어서 `category`, `topic`, `summary`, `keywords`, `entities` 같은 값을 얻어야 한다면 **AI가 값을 추출하는 단계가 필요할 수 있다.** 이를 메타데이터 추출 또는 메타데이터 보강(enrichment) 단계라고 볼 수 있다.

```text
청크 본문
  ↓
LLM·분류 모델이 의미 기반 필드 추출
  ↓
파일·파서·업무 시스템이 제공한 확정 값과 병합
  ↓
인제스트 코드가 최종 메타데이터 객체 조립
  ↓
벡터DB 저장
```

하지만 모든 메타데이터를 AI가 판독해서 만들게 해서는 안 된다.

- 파일이나 시스템이 이미 알고 있는 값은 그대로 가져온다.
- 규칙으로 정확히 계산할 수 있는 값은 일반 코드로 만든다.
- 문장의 의미를 읽어야 하는 값만 AI로 추출한다.
- 권한, 문서 ID, 버전처럼 틀리면 위험한 값은 AI에게 추론시키지 않는다.

임베딩 모델도 메타데이터 추출 AI와 역할이 다르다. 임베딩 모델은 받은 텍스트를 벡터로 바꿀 뿐, 제목·카테고리·권한 값을 반환하지 않는다. 의미 기반 메타데이터가 필요하다면 임베딩과 별개로 LLM이나 분류 모델을 호출해야 한다.

#### 어디서, 어떻게 조립하는가 — 현재 프로젝트

현재 프로젝트에는 **AI가 본문을 읽어 메타데이터를 자동 추출하는 단계가 없다.** 서버는 문서를 받을 때 호출자가 공통 메타데이터를 함께 보내도록 하고, `ingestDocument()`가 시스템 값을 추가한다.

```json
{
  "source": "휴가규정-2026.md",
  "text": "문서 전체 내용...",
  "metadata": {
    "title": "2026년 휴가 규정",
    "category": "인사",
    "year": 2026,
    "accessLevel": "employee"
  }
}
```

[`src/lib/documents.ts`](../../src/lib/documents.ts)의 `ingestDocument()`는 문서를 청킹한 뒤, 입력받은 공통 메타데이터에 시스템 필드를 합쳐 청크별 메타데이터를 만든다.

```ts
const metadatas = chunks.map((_, i) => ({
  ...input.metadata,
  source,
  chunkIdx: i,
  ingestedAt: now,
}))

await collection.upsert({ ids, documents: chunks, metadatas })
```

따라서 이 구현에서는 다음처럼 역할이 나뉜다.

- 호출자가 정해서 전달: `title`, `category`, `year`, `department`, `accessLevel` 등
- 적재 코드가 자동 생성: `source`, `chunkIdx`, `ingestedAt`
- 파서나 구조 청커를 붙일 때 추가할 값: `heading`, `page`, `parentId` 등

`source`, `chunkIdx`, `ingestedAt`은 현재 코드가 마지막에 덮어쓰는 시스템 필드다. 호출자가 같은 이름을 보내도 시스템 값이 우선하므로 예약 필드처럼 취급한다.

#### 어디에 저장되고 어떻게 쓰이는가

- **청크 본문**은 임베딩되어 의미 유사도 검색에 사용된다.
- **메타데이터**는 본문과 별도로 저장되어 필터링, 출처 표시, 권한 검사, 갱신에 사용된다.

`heading`처럼 의미 검색에도 중요하고 필터에도 필요한 정보는 한쪽만 고집할 필요가 없다. 예를 들어 `"인사규정 > 연차휴가\n..."`처럼 청크 본문 앞에 붙여 임베딩에 반영하면서, 동시에 `heading: "연차휴가"`를 메타데이터로 저장할 수 있다.

질문이 들어온 뒤에는 메타데이터를 새로 만드는 것이 아니라, 적재해둔 값을 검색 조건으로 사용한다. 그래서 **검색 이후에 필요할 정보는 적재 시점에 넣어야 한다.** 원본과의 연결이 사라진 청크만 보고 페이지, 권한, 버전을 정확히 복원하기는 어렵다.

### 3-6. 임베딩과 저장

**임베딩은 조각 하나당 연산 한 번이다.** 조각 100만 개면 임베딩 100만 개를 만들어야 한다. 다만 **API 요청 수와 임베딩 개수는 다르다** — 임베딩 API는 대개 배치 입력(한 요청에 여러 텍스트)을 받으므로 요청 수는 훨씬 줄일 수 있다. **줄어드는 건 요청 수와 왕복 지연이지 토큰 과금이 아니다.** 로컬 오픈소스 모델을 쓰면 API 비용은 0이지만 GPU나 시간을 쓴다. 자세한 원리는 [vector-db.md](../01-basics/vector-db.md) 참고.

**모델은 한 번 고르면 갈아타기가 비싸다.** 모델을 바꾸면 벡터 공간 자체가 달라져 **기존 벡터가 전부 무의미해진다.** 전체 재색인 말고 방법이 없다.

**저장 단계에서 진짜 어려운 건 최초 적재가 아니라 갱신이다.**

- **추가** — 쉽다. 조각 만들어 넣으면 된다
- **수정** — 그 문서에서 나온 **기존 조각을 전부 찾아 지우고 새로 넣어야** 한다. 조각 하나만 바뀌었어도 청킹 경계가 밀리면 전부 다시 만들어야 할 수 있다
- **삭제** — 조각을 다 지워야 하는데, 제품에 따라 삭제가 즉시 반영되지 않고 표시만 해두는 경우가 있다 (**제품별로 다르고 전부 확인하지 않음**)

**이게 캐시 무효화 문제다.** 원본은 파일 스토리지나 RDB에 있고 벡터DB는 그로부터 파생된 인덱스다. **원본 변경 이벤트를 벡터DB까지 전파하는 파이프라인이 없으면 최신성 실패는 반드시 터진다.** 도구가 대신 안 해준다.

## 4. 온라인 파이프라인

### 4-1. 질의 변환 (선택)

- **재작성** — 대화 맥락을 붙인다. "그럼 반차는요?"는 그 자체로 검색이 안 된다. 앞 대화를 보고 "반차 사용 규정은?"으로 펴줘야 한다. **LLM이 stateless라는 사실이 여기서 다시 나온다**
- **확장** — 원 질문에서 변형 질의를 여러 개 만들어 각각 검색한 뒤 합친다. 재현율이 오르고 지연과 비용이 배로 든다

**온라인 단계에서는 무엇을 추가하든 사용자가 기다리는 지연으로 되돌아온다.**

### 4-2. 검색 — 하이브리드가 사실상 기본

**두 갈래를 동시에 돌린다.**

- **벡터 검색** — 질문을 임베딩하고 ANN으로 가까운 조각을 찾는다. "연차"와 "휴가"를 이어준다
- **키워드 검색(BM25)** — 글자가 일치하는 조각을 찾는다. "이월"이라는 정확한 단어를 잡는다

**왜 둘 다 필요한가.** 임베딩은 의미를 압축하는 손실 압축이라 **글자 자체는 버려진다.** 사번, 에러코드, 제품 코드명, 사내 약어처럼 의미가 아니라 글자가 중요한 질의를 놓친다. BM25는 그걸 정확히 잘하고 대신 "연차"와 "휴가"를 못 잇는다. **둘의 약점이 정확히 반대라서 같이 쓴다.**

**두 순위를 합치는 방법.** 점수 체계가 서로 달라 그냥 못 더한다. **RRF(Reciprocal Rank Fusion)** 는 각 결과에서의 등수의 역수를 더하는 방식이라 점수 스케일을 맞출 필요가 없다.

**필터도 이 단계에 걸린다.** 권한과 버전 필터가 여기 붙고, 구현이 까다롭다. 상세는 [vector-db.md](../01-basics/vector-db.md) 참고.

### 4-3. 리랭킹 — 넓게 건지고 좁게 거른다

후보 수십 개를 다시 줄 세워 상위 몇 개만 남긴다.

**왜 두 번 하나.** 벡터 검색은 **질문과 조각을 따로따로 벡터로 만들어 거리만 잰다.** 미리 계산해둘 수 있어 빠르지만 정밀하지 않다. 리랭커(cross-encoder)는 **질문과 조각을 한 쌍으로 같이 모델에 넣어** 관련도를 뽑는다. 훨씬 정확하고 훨씬 느리다.

**그래서 2단 구조다.** 빠른 방법으로 100만 개에서 수십 개로 좁히고, 느린 방법으로 그걸 정렬한다. **DB 인덱스로 후보를 좁힌 뒤 애플리케이션에서 정밀 조건을 거는 것**과 같은 구조다.

**대가.** 후보 50개면 리랭커 추론 50회다. 후보 수가 정확도와 지연의 다이얼이 된다.

### 4-4. 프롬프트 조립

```
아래 [문서]에 근거해서만 답하라. 문서에 없으면 "모른다"고 답하라.
각 문장 끝에 근거한 문서 번호를 [1] 형식으로 표기하라.

[문서 1] (인사규정 2026 개정, 제23조, 18쪽)
제23조(연차휴가) ... 미사용 연차는 익년도로 이월하지 아니한다 ...

[질문] 작년에 못 쓴 연차 이월되나요?
```

**결정할 것들.**

- **몇 개를 넣나(top-k)** — 많이 넣으면 재현율이 오르고 중간 손실과 비용이 는다
- **순서를 어떻게 두나** — 중간이 흐려지므로 **중요한 조각을 맨 앞이나 맨 뒤에** 배치한다
- **메타데이터를 같이 넣나** — 문서명과 날짜를 넣어야 모델이 "2026년 개정본 기준"이라고 답할 수 있고 출처도 붙는다

### 4-5. 생성과 후처리

**환각은 여기서 터진다.** 문서에는 "이월하지 않는다"고 적혀 있는데 모델이 일반 상식으로 "일부 이월 가능하다"고 답하거나, 출처 `[1]`은 붙었는데 그 문서에 그런 내용이 없는 경우다.

**냉정하게 짚을 것. 프롬프트로 "문서에만 근거하라"고 지시하는 건 완화일 뿐 보장이 아니다.** 모델의 확률적 생성을 제약으로 강제할 수단이 없다. 줄일 수는 있어도 없앨 수는 없다.

**후처리가 마지막 그물이다.**

- **인용 검증** — 답변이 인용한 근거가 실제로 그 내용을 담고 있는지 프로그램이나 별도 LLM 호출로 대조한다
- **출처 표시** — 사용자가 원문을 확인할 수 있게 링크를 붙인다. **환각을 없애지는 못해도 사용자가 잡아낼 수 있게 만드는 게 현실적인 방어선이다**
- **거절 처리** — 검색 점수가 임계값 아래면 아예 답하지 않는다

## 5. 실패 모드 여덟 개를 단계에 못 박기 (★ 이 노트의 결론)

RAG를 기법 목록으로 외우면 안 남는다. **각 단계가 무너질 때 어떤 실패가 나는지**로 잡아야 쓸 수 있다.

| # | 실패 모드                  | 터지는 단계                        | 방어 수단                             |
| - | -------------------------- | ---------------------------------- | ------------------------------------- |
| 1 | 못 찾음 (recall)           | 파싱, 청킹, 임베딩, 질의변환, 검색 | 오버랩, 하이브리드 검색, 질의 확장    |
| 2 | 엉뚱한 걸 찾음 (precision) | 파싱, 청킹, 검색, 리랭킹           | 리랭커, 메타데이터 필터               |
| 3 | 최신성 깨짐                | 저장 (갱신 전파)                   | 증분 색인, 삭제 전파, 버전 메타데이터 |
| 4 | 권한 누수                  | 검색 (필터), 저장 구조             | 메타데이터 필터, 테넌트 분리          |
| 5 | 컨텍스트 초과와 중간 손실  | 청킹, 리랭킹, 조립                 | top-k 조절, 압축, 재정렬              |
| 6 | 근거 무시 (환각)           | 생성, 후처리                       | 프롬프트 제약, 인용 강제, 검증 단계   |
| 7 | 비용과 지연                | 전 구간                            | 캐싱, 임베딩 모델 선택, 배치          |
| 8 | 평가 불가                  | 파이프라인 바깥                    | 평가셋, RAGAS류 지표                  |

```
오프라인:  파싱 → 청킹 → 임베딩 → 저장
            ↑      ↑       ↑        ↑
           1,2   1,2,5    1,7       3
                          └ 모델 선택이 나쁘면 비용(7)만이 아니라
                            애초에 못 찾는다(1)

온라인:    질의변환 → 검색 → 리랭킹 → 조립 → 생성 → 후처리
              ↑       ↑       ↑       ↑      ↑      ↑
              1     1,2,4    2,5      5      6      6

7번은 전 구간에 누적되는 세금, 8번은 파이프라인을 밖에서 재는 장치
```

**세 가지 원칙으로 정리된다.**

- **상류의 손실은 하류에서 복구되지 않는다.** 파싱에서 깨진 표, 청킹에서 안 심은 메타데이터는 아무리 좋은 리랭커를 써도 못 살린다. **개선은 위에서 아래로 해야 한다**
- **오프라인은 비용, 온라인은 지연.** 어디에 투자할지는 어느 쪽을 감당할 수 있느냐로 갈린다
- **도구가 안 해주는 층이 있다.** 3번의 갱신 전파, 4번의 권한, 8번의 평가는 범용 오픈소스가 대신 해줄 수 없다. **권한은 그 조직의 구조를 알아야 설계할 수 있고, 평가는 그 조직의 질문 분포를 알아야 만들 수 있기 때문**이다

## 6. 오픈소스 세 갈래 (미검증 — 레포 확인 필요)

> **아래는 각 프로젝트가 표방하는 설계 방향에 대한 이해이고, 구현 세부와 현재 기능 상태를 직접 확인하지 않았다. 그대로 인용하지 말 것.**

|           | RAGFlow                           | Microsoft GraphRAG               | LightRAG                 |
| --------- | --------------------------------- | -------------------------------- | ------------------------ |
| 축        | 문서 파싱 중심 벡터 검색          | 무거운 그래프                    | 가벼운 그래프            |
| 힘준 단계 | 파싱, 청킹                        | 저장 (색인 시점에 그래프 구축)   | 저장 (그래프를 저렴하게) |
| 강점 방향 | 표와 레이아웃이 복잡한 실무 문서  | 문서 전체를 가로지르는 전역 질문 | 그래프 이점 + 증분 갱신  |
| 대가      | 무겁다, 여러 컴포넌트를 띄워야 함 | 색인 토큰 비용이 크다            | 그래프 품질은 미확인     |

⚠️ **오해 주의 — 그래프 계열이 벡터를 안 쓰는 게 아니다.** 위 표의 "무거운 그래프", "가벼운 그래프"를 벡터를 안 쓴다는 뜻으로 읽으면 안 된다. **LightRAG는 논문 초록에서 벡터를 쓴다고 명시한다**(확실). LightRAG 초록은 *"The integration of graph structures with vector representations facilitates efficient retrieval of related entities and their relationships"*라고 적혀 있다 [출처: [arXiv:2410.05779](https://arxiv.org/abs/2410.05779), 초록 원문 확인 ✅]. 즉 **벡터가 진입점이고 그래프가 확장 경로다**. 이 구조 자체는 [rag-hybrid-walkthrough.md](../03-graphrag/rag-hybrid-walkthrough.md) 3장에서 예제로 끝까지 추적해뒀다. **GraphRAG도 마찬가지다** — 공식 문서가 로컬 검색을 *"the local search method identifies a set of entities from the knowledge graph that are **semantically-related** to the user input"*이라고 설명하고, 입력에 **Entity Description Embedding**이 들어간다 [출처: [GraphRAG 공식 문서 Local Search](https://microsoft.github.io/graphrag/query/local_search/), 원문 확인 ✅]. 즉 **임베딩으로 진입 엔티티를 찾고 거기서 관계·커뮤니티 리포트·원문 청크로 확장한다.** (RAGFlow가 벡터를 어디에 쓰는지는 레포로 확인 안 했다 🔍.)

**임베딩 대상이 다르다는 게 진짜 차이다.**

|                   | 일반 RAG                 | GraphRAG 계열                                                     |
| ----------------- | ------------------------ | ----------------------------------------------------------------- |
| 무엇을 임베딩하나 | 텍스트 청크              | 엔티티 설명, 관계, 커뮤니티 요약                                  |
| 찾은 다음         | 그대로 컨텍스트에 넣는다 | 그래프를 타고 이웃, 관계, 커뮤니티 리포트, 원문 청크까지 확장한다 |

**그래서 저장소가 셋이 된다 — 청크 임베딩, 엔티티와 관계 그래프, 커뮤니티 요약. 여기에 원문까지.** 문서 하나가 수정되면 이걸 전부 갱신해야 하고, 그게 실패 모드 3번(최신성)이 그래프 계열에서 특히 비싼 이유다.

그러니 표를 볼 때 이 축은 "벡터를 쓰냐 마냐"가 아니라 **"벡터 위에 그래프를 얼마나 얹느냐"**로 읽어야 한다.

**축을 한 줄로 정리하면** 세 프로젝트는 **"조각을 잘 찾는 것"과 "조각들 사이의 관계를 미리 계산해두는 것"** 중 어디에 투자하느냐로 갈린다. 그리고 그 투자는 **색인 비용과 질의 능력의 트레이드오프**로 정확히 환산된다.

**GraphRAG가 조각 검색으로 못 하는 걸 하는 이유** — 색인 시점에 문서에서 엔티티와 관계를 뽑아 그래프를 만들고 군집별 요약을 미리 만들어두면, "이 문서 전체에서 반복되는 주제가 뭐냐" 같은 **전역 질문**에 답할 수 있다. 조각 다섯 개를 붙여서는 절대 못 하는 일이다. 대신 문서 하나가 바뀌면 그래프를 다시 만들어야 해서 **증분 갱신이 어렵다.** (구조적 추론이며 구현 확인 필요)

> ## 📌 핵심 요약
>
> RAG는 오프라인 ETL(파싱, 청킹, 임베딩, 저장)과 온라인 조회(질의변환, 검색, 리랭킹, 조립, 생성, 후처리)가 벡터DB를 사이에 두고 붙은 구조다. 전부 프롬프트에 넣을 수 없는 이유는 윈도우, 비용, 지연이라는 하드 제약에 더해 **길수록 품질이 떨어진다**는 네 번째 이유가 있어서다. 실패 모드는 전부 특정 단계에 귀속되며, **상류 손실은 하류에서 복구되지 않으므로 파싱과 청킹, 그리고 그때 심는 메타데이터가 시스템 상한을 결정한다.** 갱신 전파와 권한과 평가는 어느 도구도 대신 해주지 않는 층이다.

> ## 🌱 심화 키워드
>
> - **Parent Document Retrieval / Sentence Window** — 작게 검색하고 크게 넣는 방식
> - **Contextual Retrieval** — 조각에 문서 맥락을 미리 붙여 저장. 색인 비용을 내고 검색 품질을 산다
> - **RRF (Reciprocal Rank Fusion)** — 점수 체계가 다른 두 순위를 등수만으로 합치는 방법
> - **Cross-encoder reranker** — 질문과 조각을 함께 넣고 점수를 매기는 정밀 모델. 느려서 상위 후보에만 쓴다
> - **HyDE** — 질문에 대한 가상의 답변을 만들어 그걸로 검색. 질문과 문서의 문체 차이를 메운다
> - **Contextual Compression** — 뽑은 조각에서 질문과 무관한 부분을 쳐내 프롬프트를 줄인다
> - **Self-RAG / CRAG** — 검색 결과가 쓸만한지 모델이 판단하고 필요하면 다시 검색하는 계열
> - **RAGAS** — RAG 평가 프레임워크. faithfulness와 answer relevancy 등으로 지표를 나눈다
