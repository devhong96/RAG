# GraphRAG — 그래프 DB를 붙인 RAG

> **한 줄 정의:** GraphRAG는 *"문서에서 엔티티와 관계를 미리 뽑아 그래프로 저장해두고, 벡터 검색이 못 잡는 **구조적 연결**을 질의 시점에 끌어오는"* RAG다. 색인 비용을 더 내고 질의 능력을 사는 구조다.

> 관련 문서:
> - [vector-db.md](../01-basics/vector-db.md) — 임베딩과 ANN 인덱스. 이 노트가 "못 한다"고 말하는 쪽의 원리
> - [rag-pipeline.md](../02-pipeline/rag-pipeline.md) — 오프라인/온라인 파이프라인 전체와 실패 모드
> - [rag-overall-flow.md](../01-basics/rag-overall-flow.md) — 코드 관점의 실행 순서
> - [rag-hybrid-walkthrough.md](../03-graphrag/rag-hybrid-walkthrough.md) — **같은 구조를 예제 하나로 끝까지 추적한 워크스루.** 이 노트가 "왜 그렇게 짜나"라면 그쪽은 "단계마다 데이터가 어떤 모양인가". 4장을 볼 때 같이 펴놓으면 좋다

> **확신도 표기 원칙** — 그래프 자료구조와 파이프라인 구조는 확실, 실행 순서·비용 배수 같은 "실무 관행"은 **추측 또는 미검증**으로 명시한다. 개별 제품(Neo4j, MS GraphRAG)의 구현 세부는 직접 확인하지 않았다.

> **용어 주의 (★)** — 이 노트의 "하이브리드"는 **벡터 + 그래프**를 뜻한다. 업계에서 "하이브리드 검색"이라고 하면 압도적으로 **벡터 + BM25(키워드)**를 가리키므로([vector-db.md](../01-basics/vector-db.md) 5장), 밖에서 말할 때는 이쪽을 **GraphRAG**로 부르는 게 안전하다.

## 1. 배경 — RAG는 왜 파인튜닝이 아닌가

LLM에 사내 지식을 넣는 길은 크게 둘이다.

- **파인튜닝** — 사전학습된 가중치 **위에** 추가 학습을 얹는다. (from scratch가 아니다. 밑바닥부터 가르치는 건 pre-training이고 그건 개인·중소기업이 할 수 있는 일이 아니다.)
- **RAG** — 가중치는 그대로 두고, 질문할 때마다 관련 문서를 검색해 프롬프트에 실어 보낸다.

**사내 지식 주입에서 RAG를 고르는 이유는 "파인튜닝이 비싸서"가 아니다.** LoRA 같은 경량 기법이 나온 뒤로 비용 격차는 예전만큼 결정적이지 않다. 진짜 이유는 둘이다.

- **갱신 주기.** 규정 한 줄이 바뀌면 RAG는 문서만 교체하면 되지만, 파인튜닝은 다시 학습해야 한다.
- **출처 추적.** 파인튜닝된 모델은 **어떤 문서에 근거해 답했는지 짚을 수 없다.** 가중치에 녹아버렸기 때문이다. RAG는 검색해온 조각이 그대로 근거가 되므로 출처를 붙일 수 있다. 사내 시스템에서는 이게 결정적이다.

*(정리하면 파인튜닝은 **말투와 형식**을 가르치는 데 강하고, RAG는 **사실과 지식**을 대는 데 강하다. 둘은 배타적이지 않고 같이 쓰기도 한다.)*

## 2. 벡터 검색만으로 안 되는 지점

초기 RAG는 **임베딩 + 벡터 DB**로 문서를 찾았다. 임베딩은 텍스트를 고정 길이 실수 배열로 바꾸는 함수이고, 뜻이 비슷한 문장은 좌표가 가깝게 찍힌다. 그래서 "결제가 안 돼요"로 물어도 "결제 실패" 문서가 걸린다. (자세한 원리는 [vector-db.md](../01-basics/vector-db.md) 1~3장.)

**한계는 검색 단위가 "텍스트 조각"이라는 데서 나온다.** 벡터 검색은 조각 하나하나를 독립적으로 보고 질문과의 거리만 잰다. 그래서 **여러 문서에 흩어진 사실을 이어 붙여야 답이 나오는 질문**에 약하다.

- "A문서 작성자가 B팀 소속인가?" — 작성자 정보는 A문서에, 소속 정보는 인사 문서에 있다. **두 조각을 잇는 건 검색이 아니라 조인이다.**
- "이 장애와 같은 원인으로 터진 과거 사례가 뭐냐?" — "같은 원인"이라는 관계가 텍스트에 문자로 적혀 있지 않으면 못 찾는다.
- "이 문서 전체에서 반복되는 주제가 뭐냐?" — 조각 다섯 개를 뽑아서는 원리적으로 답할 수 없는 **전역 질문**이다.

**핵심은 "벡터 DB가 멍청하다"가 아니라 "조각 단위 유사도라는 접근 경로로는 표현할 수 없는 질의가 있다"는 것이다.** RDB에 인덱스가 있어도 조인 없이는 못 푸는 질의가 있는 것과 같은 종류의 한계다.

## 3. Graph DB — 관계를 1급 시민으로 저장한다

데이터를 표가 아니라 **점(Node, 개체)**과 **선(Edge, 관계)**으로 저장한다.

```
[노드: 김철수] --(엣지: 소속팀)--> [노드: 결제개발팀]
[노드: 문서#405] --(엣지: 작성자)--> [노드: 김철수]
```

### 왜 RDBMS로 안 하나

**"JOIN이 무거워서"라고만 말하면 반쯤만 맞다.** 정확히는 **홉 하나의 비용 특성**이 다르다.

| | RDBMS | Graph DB |
|--|--|--|
| 관계 한 칸 타기 | 인덱스 조회 **O(log n)** — n은 테이블 전체 행 수 | 인접 리스트 따라가기 **O(1)** — 전체 크기와 무관 |
| 깊이 k 탐색 | O(log n)을 k번 반복 + 중간 결과 팽창 | O(1)을 k번 |
| 깊이가 가변일 때 | SQL로 표현 자체가 괴롭다 (재귀 CTE) | 쿼리 언어에 내장 (`[:REL*1..3]`) |

이걸 **Index-Free Adjacency(인덱스 없는 인접성)**라고 부른다. 노드 레코드가 자기와 연결된 엣지 레코드를 **직접 가리키고 있어서**, 이웃을 찾을 때 인덱스를 다시 뒤지지 않는다.

> ⚠️ **정밀화** — 흔히 "엣지가 물리적 메모리 주소를 갖고 있다"고 설명되지만(Neo4j 문서·마케팅 표현), 실제로는 **고정 크기 레코드 구조**라서 `레코드 ID × 레코드 크기`로 **파일 오프셋을 산술 계산**해 바로 찾아가는 쪽에 가깝다. 대상은 메모리가 아니라 스토어 파일(과 페이지 캐시)이다. "포인터를 따라간다"는 **비유**로는 맞지만 문자 그대로는 부정확하다. (**Neo4j 기준 이해이며 저장 엔진 코드까지는 확인 안 함**)

**중요한 건 상수 배 빠르다는 게 아니라 "전체 데이터가 아무리 커져도 홉 비용이 안 늘어난다"는 점이다.** 그래서 깊이가 깊어질수록 격차가 벌어진다. 반대로 **깊이 1~2짜리 단순 관계라면 RDBMS로도 충분하다** — 그래프 DB를 도입할 이유가 안 된다.

## 4. 하이브리드 파이프라인 (벡터 + 그래프)

벡터의 **의미적 유연성**과 그래프의 **구조적 정확성**을 섞는다. 대표 구현이 Microsoft GraphRAG다. (**설계 방향에 대한 이해이고 구현 세부는 미확인** — [rag-pipeline.md](../02-pipeline/rag-pipeline.md) 6장과 같은 단서다.)

### Step 1. 오프라인 색인 (Data Ingestion)

문서를 청킹한 뒤 **두 갈래로 나눠 적재**한다.

- **Vector 경로** — 조각을 임베딩해 벡터 DB에 넣는다.
- **Graph 경로** — 조각을 LLM에 통과시켜 *"핵심 인물·날짜·문서를 노드로, 그 관계를 엣지로 뽑아줘"*라고 시킨다. 뽑힌 노드와 엣지를 Graph DB에 넣는다.

**여기가 이 아키텍처의 진짜 비용 지점이다** (7장 참고).

### Step 2. 온라인 검색 (Retrieval)

질문: *"최근 결제팀 장애 보고서 요약해줘"*

두 DB를 엮는 방식은 크게 둘이고, **어느 쪽이 "보통"인지는 단정할 근거가 없다** (**추측 섞임**).

- **순차형 (entry point → 확장)** — 벡터 검색으로 그래프 탐색을 시작할 **진입 노드**를 먼저 찾고(예: `문서 #405`), 그 노드를 중심으로 그래프를 펼쳐 `[담당자]`, `[과거 유사 장애]` 같은 관계망을 끌어온다. MS GraphRAG의 local search가 이 계열로 알려져 있다.
- **병렬형 (각자 검색 후 융합)** — 벡터 검색과 그래프 검색을 동시에 돌리고 결과를 합친다. 순위 융합에는 [RRF](../01-basics/vector-db.md)를 쓴다.

전역 질문("이 조직에서 반복되는 장애 패턴이 뭐냐")에는 색인 시점에 미리 만들어둔 **커뮤니티 요약**을 쓰는 경로가 따로 있다 (MS GraphRAG의 global search. **구조적 이해이며 구현 미확인**).

### Step 3. 생성 (Generation)

LLM에 세 가지를 함께 넘긴다.

- 벡터 검색이 가져온 **텍스트 본문 조각**
- 그래프 검색이 가져온 **팩트 관계망**
- 사용자의 **원래 질문**

## 5. 최대 병목 — Supernode와 3중 제동 (★)

그래프 탐색에서 실무적으로 가장 먼저 터지는 게 **Supernode(슈퍼노드)** 문제다. 연결 차수가 비정상적으로 높은 노드(전사 공지, 대표이사, 공통 라이브러리)를 만나면 탐색 결과가 폭발한다.

```
노드 A → 부서원 50명 → 그들이 쓴 문서 1만 개 → 연관 서버 500대
```

**여기서 뭐가 죽는지를 정확히 구분해야 한다.** 두 개는 다른 층위의 사고다.

- **DB 층** — 탐색 중간 결과를 메모리에 쌓다가 **쿼리 타임아웃이나 OOM**이 난다. 서버가 실제로 위험한 건 이쪽이다.
- **LLM 층** — 살아남아 프롬프트까지 갔어도 **토큰 한도 초과로 API가 에러(400)를 반환**한다. 내 서버가 죽는 게 아니라 요청이 거절되는 것이다.

그래서 Cypher 쿼리에 **3중 브레이크**를 건다.

1. **깊이(Depth) 제한** — `[:REL*1..2]`처럼 홉 수를 못 박는다.
2. **관계 종류(Type) 필터** — 모든 엣지를 타지 말고 `[:원인_제공]`, `[:해결됨]`처럼 **의미 있는 관계만** 탄다. Supernode 방어에는 이게 깊이 제한보다 효과가 크다 (**판단이며 정량 근거 없음**).
3. **개수 제한(LIMIT)** — 점수 상위 N개만 자른다.

**결국 품질을 만드는 건 LLM의 지능이 아니라, 무엇을 넣고 무엇을 버릴지 정하는 검색 설계다.** 백엔드 개발자가 손대는 층이 정확히 여기다.

## 6. 최종 단계에서 LLM이 하는 일

검색 DB가 자료를 찾아오는 사서라면, LLM은 자료를 읽고 답안을 쓰는 수험생이다. 하는 일은 셋이다.

- **종합(Synthesis)** — 투박한 문장 조각과 `{노드: 철수, 관계: 작성, 타겟: 문서A}` 같은 기계적 구조를 사람이 읽을 글로 융합한다.
- **추론(Reasoning)** — "문서A 작성자=철수", "철수 소속=결제팀"이라는 **파편화된 팩트를 이어** *"결제팀이 문서A를 작성했다"*는 결론을 만든다. 그래프가 팩트를 대주고 LLM이 잇는 분업이다.
- **지시 수행(Instruction Following)** — "표로 그려줘", "쉽게 설명해줘" 같은 형식 요구를 처리한다.

**주의.** 2번의 추론은 검색이 제대로 된 경우에만 의미가 있다. 그래프가 틀린 관계를 뽑아 넣었으면 LLM은 **틀린 팩트 위에서 그럴듯하게 추론한다.** 색인 시점 LLM 추출 품질이 그대로 상한이 된다.

## 7. 도입 판단 — Indexing Cost (★ 트레이드오프)

하이브리드의 최대 허들은 **초기 색인 비용(Indexing Cost)**이다. 벡터 전용은 조각마다 임베딩 한 번이면 끝나지만, 그래프 경로는 **조각마다 LLM을 한 번씩 태워** 노드와 엣지를 뽑아야 한다.

> ⚠️ **이 비용은 기하급수(exponential)가 아니다.** 조각 수에 대략 **선형**이다. 다만 **단가 상수가 크다** — 임베딩 호출 대비 LLM 추출 호출은 토큰당 단가도 비싸고 출력 토큰도 발생하므로 자릿수 단위로 벌어진다. (**배수는 모델·프롬프트에 따라 크게 달라 수치를 적지 않는다**)

**갱신 비용도 같이 봐야 한다.** 문서 하나가 바뀌면 그 조각의 노드·엣지를 다시 뽑아야 하고, 커뮤니티 요약까지 쓰는 구조라면 요약도 다시 만들어야 할 수 있다. **증분 갱신이 어렵다**는 게 그래프 계열의 알려진 약점이다 (LightRAG가 이 지점을 노린 프로젝트. [rag-pipeline.md](../02-pipeline/rag-pipeline.md) 6장, **미검증**).

**판단 기준은 단순하다.** 질문이 *"연차 이월되나요"* 류의 **국소 조회**라면 벡터만으로 충분하고 그래프는 과잉이다. *"이 장애의 근본 원인 계통을 추적해줘"*, *"전사에서 반복되는 패턴이 뭐냐"* 같은 **관계 추적·전역 질문**이 실제 요구에 있을 때만 값을 한다.

---

> ## 📌 핵심 요약
> GraphRAG는 색인 시점에 LLM으로 엔티티와 관계를 뽑아 그래프로 저장해두고, 벡터의 조각 단위 유사도로는 표현할 수 없는 **관계 추적·전역 질문**을 처리하는 구조다. 그래프 DB가 빠른 이유는 Index-Free Adjacency — 홉 비용이 전체 데이터 크기와 무관해 깊이가 깊어질수록 RDBMS와 벌어진다. 실무 병목은 Supernode이고, 깊이·관계 타입·LIMIT의 3중 제동으로 막는다. 대가는 초기 색인 비용(조각 수에 **선형**이지만 단가 상수가 큼)과 **증분 갱신의 어려움**이며, 국소 조회만 필요한 시스템에는 과잉이다.

> - **Knowledge Graph** — 지식을 노드·엣지 네트워크로 형상화한 구조. 검색엔진의 엔티티 이해에 쓰인다
> - **Community Detection / 커뮤니티 요약** — 그래프를 군집으로 나눠 군집마다 요약을 미리 만들어두는 기법. GraphRAG의 전역 질문 능력이 여기서 나온다
> - **Cypher / 가변 길이 경로** — `[:REL*1..3]` 문법과 그 비용 특성
> - **Supernode / 차수 편중** — 고차수 노드가 탐색을 폭발시키는 문제
> - **Entity Resolution** — LLM이 뽑은 "김철수"와 "철수 님"을 같은 노드로 합치는 문제. 그래프 품질의 실질적 상한

> ## ❓ 남은 질문
> 1. LLM이 뽑은 엔티티의 **동일인 판정(Entity Resolution)**은 어떻게 하나? "결제팀"과 "결제개발팀"이 별개 노드로 갈리면 그래프가 조용히 망가지는데, 이걸 자동으로 잡을 수 있나?
> 2. 그래프 추출 품질을 **어떻게 측정**하나? 검색 실패와 달리 "관계를 잘못 뽑았다"는 최종 답변만 봐서는 안 드러난다.
> 3. 깊이 제한과 관계 타입 필터 중 Supernode 방어에 실제로 더 효과적인 건 어느 쪽인가? 측정해본 사례가 있나?
> 4. 내 프로젝트 규모에서 그래프까지 필요한가 — 실제 질문 로그를 모아보면 국소 조회와 관계 추적의 비율이 어떻게 나올까?
