# 하이브리드 RAG 워크스루 — 데이터가 단계마다 어떻게 변형되는가

> 문서 한 건과 질문 하나를 고정해놓고, **파싱부터 프롬프트 조립까지 각 단계에서 데이터의 모양이 실제로 어떻게 바뀌는지** 끝까지 따라간다. 벡터DB와 그래프DB를 둘 다 붙인 구성 기준.

> 관련 문서:
>
> - [rag-graphdb-hybrid-pipeline.md](../03-graphrag/rag-graphdb-hybrid-pipeline.md) — 같은 구조를 **설계 선택지와 트레이드오프** 관점에서 다룬 노트. 이 노트가 "무엇이 흘러가나"라면 그쪽은 "왜 그렇게 짜나"
> - [rag-pipeline.md](../02-pipeline/rag-pipeline.md) — 단계별 실패 모드
> - [rag-overall-flow.md](../01-basics/rag-overall-flow.md) — 컴포넌트 역할과 오개념
> - [vector-db.md](../01-basics/vector-db.md) — 벡터DB 내부

> **수치 표기 원칙** — 이 노트의 조각 개수·후보 개수·차원 수는 **감을 잡기 위한 예시값**이고 규칙이 아니다. 실제 값은 문서 성격과 모델에 따라 크게 다르다.

## 0. 추적 예제 고정

|                  |                                                                                                       |
| ---------------- | ----------------------------------------------------------------------------------------------------- |
| **문서**   | `인사규정_2026개정.pdf` (50페이지, 표 포함)                                                         |
| **질문 A** | `"작년에 못 쓴 연차 이월되나요?"` — 벡터만으로 충분한 유형                                         |
| **질문 B** | `"2026년 개정에서 연차 조항이 바뀌었는데, 영향받는 다른 규정이 뭐가 있나?"` — 그래프가 필요한 유형 |

두 질문을 나란히 두는 이유가 있다. **하이브리드가 왜 필요한지는 A만 봐서는 절대 안 보인다.** A는 벡터DB 하나로 끝나기 때문이다.

## 1. 전체 지도

```
                        인사규정_2026개정.pdf
                                 │
                                 ▼  파싱 (포맷 변환)
                           텍스트 + 구조
                                 │
                                 ▼  청킹 (분할 + 메타데이터 부착)
                            조각 수만 개
                                 │
     ┌───────────────────────────┴───────────────────────────┐
     ▼ 갈래 A                                                 ▼ 갈래 B
   임베딩                                              엔티티·관계 추출
 (조각당 1회)                                        (조각당 LLM 1회 ★비쌈)
     │                                                        │
     ▼                                                        ▼
  벡터DB 적재                                            그래프DB 적재
  + ANN 인덱스                                          (노드 / 엣지)
     │                                                        │
     └───────────────────── 공통 키로 연결 ──────────────────────┘
                          (chunk_id / doc_id)

════════════════ 여기까지 오프라인 배치. 질문 오기 전에 끝. ════════════════

                             질문 도착
                                 │
     ┌───────────────────────────┴───────────────────────────┐
     ▼                                                        ▼
  질문 임베딩                                            엔티티 추출
 (색인 때와 같은 모델)                                 "연차", "2026 개정"
     │                                                        │
     ▼                                                        ▼
  벡터DB 검색                                          그래프DB 트래버설
  "뜻이 가까운 문단"                                   "연결된 것 따라가기"
     │                                                        │
     ▼                                                        ▼
  조각 30개                                              관계 경로 N개
     │                                                        │
     └───────────────────────────┬───────────────────────────┘
                                 ▼
                            결과 융합 (RRF 등)
                                 ▼
                          리랭킹 → 5~10개
                                 ▼
                    프롬프트 조립 ★ 관계를 텍스트로 직렬화
                                 ▼

```

**이 그림에서 제일 중요한 선은 가운데 이중선이다.** 위는 배치, 아래는 요청 경로. 실행 주기도 성능 예산도 장애 성격도 다르다.

## 2. 오프라인 — 질문이 오기 전에

### 2-1. 파싱

**입력** PDF 바이너리 → **출력** 텍스트 + 구조 정보

```
"제12조(연차휴가의 이월)\n미사용 연차는 익년 3월 31일까지 이월한다.
 본 조는 2023년 규정 제9조를 개정한 것이며, 정규직에 한해 적용한다."
 + { 제목 계층: 제3장 > 제12조, 페이지: 14 }
```

**여기서 깨지면 하류에서 복구되지 않는다.** 표가 무너지거나 2단 조판이 섞이면 아래 모든 단계가 그 위에서 돈다. 상세는 [rag-pipeline.md](../02-pipeline/rag-pipeline.md) 3-1.

### 2-2. 청킹

**입력** 문서 전체 텍스트 → **출력** 조각 + **메타데이터**

여기서 붙는 메타데이터가 나중에 두 창고를 잇는 열쇠가 된다. 그냥 자르기만 하면 안 된다.

```json
{
  "chunk_id": "hr2026-c12-03",
  "text": "제12조(연차휴가의 이월) 미사용 연차는 익년 3월 31일까지 이월한다...",
  "doc_id": "hr2026",
  "version": "2026",
  "page": 14,
  "section": "제12조"
}
```

**이 시점에는 아직 벡터도 그래프도 없다.** 순수한 텍스트 조각과 꼬리표뿐이다.

### 2-3. 갈래 A — 임베딩과 벡터DB 적재

**입력** 조각 텍스트 → **출력** 실수 배열

```
"제12조(연차휴가의 이월) 미사용 연차는..."
        │
        ▼  임베딩 모델
[0.021, -0.184, 0.077, ... ]      ← 384개 (all-MiniLM-L6-v2 기준, 거의 확실)
```

📖 **이 숫자가 뭔지, 384가 어디서 온 수인지는 [vector-db.md](../01-basics/vector-db.md) 1장으로 넘긴다.** 요점만 — **384는 모델 구조가 정한 상수**이고, **각 차원에는 사람이 읽을 수 있는 이름이 없다.** 의미는 값 자체가 아니라 다른 벡터와의 **상대적 거리**에만 있다.

저장할 때 **벡터만 넣으면 안 된다.** 원문 텍스트를 같이 저장한다 — 나중에 LLM에 실어야 하는데 벡터에서 텍스트로 되돌릴 방법이 없기 때문이다.

```json
{ "chunk_id": "hr2026-c12-03", "vector": [...], "text": "제12조...", "metadata": {...} }
```

그리고 **ANN 인덱스를 구축한다**. 이게 "색인"의 실체다 — 벡터를 넣는 것과 찾을 수 있게 만드는 것은 별개 작업이다 ([vector-db.md](../01-basics/vector-db.md) 3장).

### 2-4. 갈래 B — 엔티티·관계 추출과 그래프DB 적재

**입력** 같은 조각 텍스트 → **출력** 노드와 엣지

같은 조각을 **한 번 더**, 이번엔 LLM에 넣는다.

```
"제12조(연차휴가의 이월) 미사용 연차는 익년 3월 31일까지 이월한다.
 본 조는 2023년 규정 제9조를 개정한 것이며, 정규직에 한해 적용한다."
        │
        ▼  LLM: "등장하는 개체와 관계를 뽑아라"
노드:  (제12조:조항)  (제9조:조항)  (정규직:직군)  (인사규정2026:문서)
엣지:  (제12조) -[개정함]->   (제9조)
       (제12조) -[적용대상]-> (정규직)
       (인사규정2026) -[포함]-> (제12조)
```

**저장 단위가 완전히 다르다.** 벡터DB는 "이 문단이 무슨 뜻인가"를, 그래프DB는 "이것과 저것이 어떻게 얽혔나"를 저장한다. 그래프는 원문 문장을 들고 있지 않다.

⚠️ **여기가 이 아키텍처의 비용 지점이다.** 조각이 5만 개면 LLM을 5만 번 호출한다. 임베딩보다 회당 단가가 훨씬 비싸고 느리다. 판단 기준은 [rag-graphdb-hybrid-pipeline.md](../03-graphrag/rag-graphdb-hybrid-pipeline.md) 7장.

#### 두 갈래는 서로를 안 본다

임베딩은 추출 결과가 필요 없고 추출도 마찬가지라, **병렬로 돌려도 된다.** 다만 2-5의 **엔티티 병합만은 추출이 전부 끝나야** 시작할 수 있다.

#### 검색용 입도와 추출용 입도는 다르다 (★)

여기가 청킹을 공유할 때 치르는 대가다. **관계 추출은 더 넓은 문맥에서 잘 된다.** 검색용으로 작게 자른 조각에 LLM을 넣으면 이런 일이 생긴다.

```
조각 A: "...본 조는 2023년 규정을"          ← 문장이 경계에서 끊김
조각 B: "제9조를 개정한 것이며..."

→ A만 보면 "무엇을" 개정했는지 모른다
→ B만 보면 "누가" 개정했는지 모른다
→ (제12조)-[개정함]->(제9조) 엣지가 아예 안 뽑힌다
```

**조각 경계에 걸친 관계는 추출 자체가 안 된다.** 벡터 쪽에서는 조각이 걸리기라도 하지만, 그래프 쪽에서는 **엣지가 애초에 생기지 않아 없는 사실이 된다.**

오버랩이 이걸 완화하지만 해결하지는 못한다. **오버랩 폭보다 논리가 길면 여전히 깨진다** — [rag-pipeline.md](../02-pipeline/rag-pipeline.md) 3-3의 한계와 같은 성질이다.

⚠️ **다만 "크면 클수록 좋다"는 아니다.** 너무 큰 덩어리를 넣으면 LLM이 관계를 누락하거나 없는 관계를 지어낸다. 넓은 문맥이 유리한 것이지 무한정 유리한 게 아니다.

그래서 구현이 갈린다.

|                              | 장점                                               | 대가                                                                         |
| ---------------------------- | -------------------------------------------------- | ---------------------------------------------------------------------------- |
| **같은 청킹 공유**     | 단순하다.`chunk_id`로 바로 이어진다              | 관계 추출 품질을 검색용 입도에 맞춰 희생                                     |
| **갈래마다 다른 입도** | 그래프는 섹션 단위로 크게 넣어 관계를 더 잘 뽑는다 | 두 창고의 단위가 어긋나**별도 매핑이 필요**하다 (방식은 구현마다 다름) |

**한쪽으로 옮겨서 푸는 문제가 아니다.** 좁히면 그래프가 죽고 넓히면 벡터가 죽는다. 다만 실무의 기울기는 **작은 쪽**이다 — 검색이 실패하면 답 자체가 안 나오지만, 관계가 몇 개 덜 뽑혀도 벡터 검색은 살아 있다. **검색이 1차, 그래프가 보강**이라는 순서 때문이다. (관행 단정이 아니라 **판단**이다)

🏷️ **출구는 이미 나온 발상에 있다** — [rag-pipeline.md](../02-pipeline/rag-pipeline.md) 3-4의 *"검색 단위와 투입 단위를 분리한다"*(small-to-big)를 관계 추출에도 적용하는 구성. **논리적으로 타당한 설계이지 표준 관행이라 단정할 근거는 없다.**

- **벡터 색인** — 작게 잘라 선택도를 산다
- **관계 추출** — 그 조각이 속한 **부모 섹션을 통째로** LLM에 넣어 관계를 뽑는다
- 뽑힌 노드의 `source_chunk_id`에는 **그 섹션에 속한 작은 조각들의 ID를 배열로** 달아둔다

둘 다 얻는 대신 부모-자식 구조를 관리해야 한다. 위 표의 "갈래마다 다른 입도"가 이 형태다.

**★ 청킹 크기가 여기서 두 번째 얼굴을 보인다.** [rag-pipeline.md](../02-pipeline/rag-pipeline.md) 3-2가 "잘게 자르면 걸렸는데 뜻을 모른다"는 벡터 쪽 손실을 다뤘다면, 그래프 쪽 손실은 **"관계가 경계에 걸려 아예 안 뽑힌다"**로 나타난다. 같은 원인에서 나온 두 가지 손실이고, 그래프를 붙이면 **작게 자르는 쪽의 대가가 한 겹 더 늘어난다.**

### 2-5. 두 창고를 잇는 공통 키 (★)

두 갈래가 따로 놀면 온라인에서 합칠 수가 없다. **노드를 만들 때 출처 조각의 ID를 같이 심어둔다.**

```
(제12조:조항 { source_chunk_id: ["hr2026-c12-03"], doc_id: "hr2026" })
```

#### `chunk_id`와 `doc_id`는 같은 층위가 아니다

**부모-자식 관계**다. RDB로 옮기면 `doc_id`가 부모 테이블 PK, `chunk_id`가 자식 테이블 PK다. 조각은 문서 없이 존재할 수 없다.

```
doc_id: "hr2026"                    ← 원본 문서 한 건 (인사규정_2026개정.pdf)
   ├─ chunk_id: "hr2026-c01-01"     ← 그 문서를 자른 조각들
   ├─ chunk_id: "hr2026-c12-03"
   └─ ... (수천 개)
```

둘 다 들고 다니는 이유는 **쓰이는 자리가 다르기 때문**이다.

|                        | 필요한 상황                           | 예                                                                                    |
| ---------------------- | ------------------------------------- | ------------------------------------------------------------------------------------- |
| **`chunk_id`** | 조각**하나를 정확히 지목**할 때 | 그래프 노드에서 원문 텍스트 환원, RRF 융합의 랭킹 단위, 리랭커 입력                   |
| **`doc_id`**   | 문서를**통째로 다뤄야** 할 때   | 문서 폐기 시 조각 수천 개 일괄 삭제, 권한 필터링, 버전(2023판/2026판) 구분, 출처 표시 |

★ **권한 쪽이 특히 아프다.** `doc_id`를 안 심어두면 검색 결과를 사용자 권한으로 거를 방법이 없다. 조각 텍스트만 봐서는 그게 어느 문서에서 왔는지 알 수 없으므로, **볼 권한이 없는 문서 내용이 답변에 섞여 나간다** ([vector-db.md](../01-basics/vector-db.md) 6장).

#### "공통 키를 만든다"기보다 "참조를 복사해둔다"

새로 발급하는 별도의 키가 아니다. **`chunk_id`는 청킹할 때 이미 태어났고, 그래프 노드는 그 값을 복사해서 들고 있을 뿐**이다. FK를 드는 것과 같다.

```
청킹 시점       chunk_id "c12-03" 발급          ← 여기서 생김
    │
    ├─→ 벡터DB    { chunk_id: "c12-03", vector: [...], text: "제12조..." }
    └─→ 그래프DB  (제12조:조항 { source_chunk_id: ["c12-03"] })
                                  ↑ 새로 만든 게 아니라 복사해온 값
```

**별도의 매핑 테이블도, "연결하는 작업"이라는 단계도 없다.**

#### 언제 박히나 — 추출하면서 그 자리에서

따로 도는 패스가 아니다. 2-4에서 노드를 뽑을 때 **그 조각의 ID를 이미 손에 들고 있으니** 그대로 써넣는다.

```python
# 흐름 설명용 의사코드 (실제 API 아님)
for chunk in chunks:
    nodes, edges = llm_extract(chunk.text)

    for n in nodes:
        n.source_chunk_id = [chunk.chunk_id]   # ← 지금 다루는 조각. 이미 알고 있다
        n.doc_id = chunk.doc_id

    graph.upsert(nodes, edges)                 # 없으면 생성, 있으면 병합
```

**"색인 때 안 심으면 나중에 못 만든다"는 말이 여기서 나온다.** 이 루프를 지나고 나면 어느 노드가 어느 조각에서 나왔는지 역추적할 방법이 사라진다. 노드 이름만 보고는 알 수 없다.

#### 두 창고의 저장 단위가 다르다 (★)

*"청킹 단위로 두 DB 결과가 만들어진다"*는 맞지만, **그래프 쪽에서 조각은 "추출의 입력 단위"이지 "저장 단위"가 아니다.** 그래프의 저장 단위는 조각이 아니라 **엔티티**다.

```
조각 1개  ──→  벡터 1개                         1 : 1   (표준 구성 기준)
조각 1개  ──→  노드 N개 + 엣지 M개               1 : N
                    ↓ 엔티티 병합 후
              노드 1개가 조각 여러 개를 가리킴      N : M
```

⚠️ 벡터 쪽 1:1도 절대적이진 않다. 조각 하나를 벡터 여러 개로 표현하는 멀티벡터(late interaction) 방식이면 여기도 1:N이 된다.

**이 차이가 삭제에서 터진다.**

|                    | 문서 한 건을 지울 때                                                                                                                                    |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **벡터DB**   | 조각과 레코드가 1:1이라`doc_id`로 일괄 삭제하면 끝                                                                                                    |
| **그래프DB** | `(제12조)` 노드의 `source_chunk_id`가 `["c12-03", "c88-05", "c41-01"]`인데 그중 하나만 삭제 대상이면 **노드를 지울 수도 안 지울 수도 없다** |

그래프 쪽은 매번 **판단**이 든다. 배열에서 해당 ID를 빼고 → 남은 출처가 있으면 노드 유지, 비었으면 삭제 → 그리고 그 노드에 붙어 있던 **엣지들도 함께 처리**해야 한다 (Cypher에서 노드 삭제에 `DETACH DELETE`가 필요한 이유가 이거다).

**"문서 하나 지웠는데 그래프에 유령 노드가 남는"** 사고가 여기서 나온다. 유령 노드는 에러를 내지 않고, 트래버설에 계속 걸려서 **이미 폐기된 규정을 근거로 답이 나간다.**

#### 엔티티 병합 — 여기만 별도 패스가 필요하다

같은 대상이 조각마다 다른 표기로 등장한다.

```
조각 c12-03 → (제12조:조항)
조각 c88-05 → (인사규정 제12조:조항)             ← 같은 것인데 노드가 따로 생김
조각 c41-01 → (제12조(연차휴가의 이월):조항)      ← 얘도 같은 것
```

⚠️ **여기서 두 층을 구분해야 한다.**

- **이름이 정확히 일치하는 병합** — 별도 패스가 필요 없다. Cypher `MERGE` 같은 upsert가 **적재 루프 안에서 이미 처리한다.** 조각 A와 조각 B가 똑같이 `(제12조)`를 뽑았으면 그 자리에서 하나로 합쳐진다.
- **표기가 다른 동일 엔티티 판정** — 이건 **조각 하나만 봐서는 불가능하다.** `"제12조"`와 `"인사규정 제12조"`가 같은지는 전체를 다 훑어야 판단할 수 있어서, 전 조각 추출이 끝난 뒤 별도 패스로 돈다. 이걸 **Entity Resolution**이라 부른다.

병합되면 이렇게 된다.

```
(제12조:조항 { source_chunk_id: ["c12-03", "c88-05", "c41-01"] })
```

**`source_chunk_id`가 배열이어야 하는 이유가 여기서 완성된다.** 단일 값이었다면 병합할 때 둘을 버리고 하나만 남겨야 하고, 그러면 나머지 두 조각의 원문을 영영 못 꺼낸다.

#### ★ 병합이 조각을 초월한 경로를 만든다 — 그래프를 붙이는 이유 전체

**추출은 조각 단위로 국소적이지만, 병합을 거친 그래프는 전역적이다.** 이 전환이 이 아키텍처의 존재 이유다.

```
조각 c12-03에서 뽑힘:   (제12조) -[적용대상]-> (정규직)
조각 c88-05에서 뽑힘:   (제12조) -[참조됨]->  (퇴직정산 제4조)
                          ↑ 표기가 같아 하나의 노드로 병합됨

병합 후:
    (정규직) <-[적용대상]- (제12조) -[참조됨]-> (퇴직정산 제4조)
                              ↑
        이 경로는 어느 조각에도 통째로 적혀 있지 않다
```

`정규직 → 제12조 → 퇴직정산 제4조`는 **원본 문서 어디를 읽어도 한자리에 나오지 않는 연결**이다. 국소적 추출들을 병합이 하나의 망으로 꿰맨 결과로만 존재한다.

**그래프가 조각 단위로만 남는다면 벡터DB와 다를 게 없다.** 조각을 넘어선 경로가 생기는 이 지점이, 색인 비용을 몇 배로 치르고 사는 것의 실체다.

⚠️ **병합이 틀리면 조용히 망가진다.** 서로 다른 조항을 같은 노드로 합치면 관계가 뒤엉키고, 반대로 같은 걸 못 합치면 **그래프가 조각조각 끊겨 트래버설이 몇 홉 못 가고 멈춘다.** 어느 쪽도 에러를 내지 않는다.

#### 정리 — 키가 태어나서 쓰이기까지

```
청킹        → chunk_id 발급 (여기서 태어남)
   ├─ 임베딩 → 벡터DB 적재     (chunk_id를 PK로)
   └─ 추출   → 그래프DB 적재   (chunk_id를 참조로 복사, upsert로 동명 노드는 즉시 병합)
                    ↓
              엔티티 병합       ← 여기만 별도 패스. source_chunk_id가 배열로 합쳐짐
```

이 키 하나가 온라인에서 **세 군데**에 쓰인다. 셋 다 이게 없으면 성립하지 않는다.

| 쓰임                  | 방향           | 하는 일                                                                                  |
| --------------------- | -------------- | ---------------------------------------------------------------------------------------- |
| **진입점 찾기** | 벡터 → 그래프 | 벡터로 걸린 조각에서 뽑힌 노드를 찾아 트래버설 시작점으로 삼는다 (3-3)                   |
| **텍스트 환원** | 그래프 → 벡터 | 트래버설로 찾은 노드의**원문 문장을 꺼내온다.** 그래프는 문장을 안 들고 있다 (3-4) |
| **융합 기준**   | 양쪽           | 두 결과를 같은`chunk_id` 랭킹으로 만들어야 순위 융합이 가능하다 (3-4)                  |

⚠️ **이게 유일한 연결 방법은 아니다.** 엔티티 이름을 직접 매칭하거나, 노드에 텍스트 스니펫을 중복 저장해 환원을 생략하는 구현도 있다. 다만 어떤 방식이든 **색인 시점에 연결 고리를 심어놓지 않으면 나중에 만들 수 없다**는 점은 같다 ([rag-pipeline.md](../02-pipeline/rag-pipeline.md) 3-5).

**청킹 전략을 바꾸면 여기가 통째로 깨진다.** 재청킹하면 `chunk_id`가 전부 새로 발급되므로, 그래프에 박혀 있던 `source_chunk_id`가 **전부 고아가 된다.** 벡터만 다시 만들면 되는 게 아니라 **그래프의 연결 고리까지 다시 심어야 한다** — 청킹 변경이 임베딩 모델 교체보다도 비싼 이유다.

## 3. 온라인 — 질문이 도착한 뒤

### 3-0. 먼저: 두 가지 형태가 있다 (★ 이걸 모르면 아래가 안 읽힌다)

온라인 파이프라인은 **순차형(= 직렬형)**과 **병렬형** 두 모양으로 갈린다. 그리고 **차이는 딱 하나다.**

```
순차형   그래프에 들어가는 입구를 "벡터 검색 결과"에서 얻는다  → 벡터를 기다린다
병렬형   그래프에 들어가는 입구를 "질문 자체"에서 뽑는다       → 안 기다린다
```

나머지 차이는 전부 여기서 파생된다. 같은 질문(질문 B)으로 나란히 추적해보자.

#### 순차형 — 벡터가 길을 안내한다

```
질문
 │
 ▼ 임베딩 → 벡터DB 검색
레코드: [c12-03, c07-01, c33-02]
 │
 ▼ ★ 여기서 입구를 얻는다
"c12-03에서 뽑힌 노드가 뭐지?"  →  (제12조)
 │
 ▼ 트래버설
(퇴직정산 제4조) 발견
 │
 ▼ text 회수 → 합침
```

**벡터가 끝나야 그래프가 출발한다.** 한 줄로 이어진다.

#### 병렬형 — 각자 알아서 찾는다

```
질문
 │
 ├──────────────────────┬──────────────────────
 ▼                      ▼
임베딩                 엔티티 추출
 │                      │  "연차", "2026 개정"
 ▼                      ▼ ★ 여기서 입구를 얻는다
벡터DB 검색            "그래프에 '연차'라는 이름의 노드 있나?"
 │                      │   →  (연차이월제도)
 │                      ▼ 트래버설
 │                     (퇴직정산 제4조) 발견
 │                      │
 │                      ▼ text 회수
 └──────────┬───────────┘
            ▼ 합침
```

**둘이 동시에 출발해서 나중에 만난다.**

#### 백엔드로 옮기면

```
순차형 = 선행 조회 결과의 ID로 후속 조회를 하는 것
         SELECT ... FROM A                  → id 획득
         SELECT ... FROM B WHERE a_id = ?   ← 앞 결과에 의존

병렬형 = 두 쿼리를 동시에 던지고 애플리케이션에서 머지
         SELECT ... FROM A  ┐ 동시 실행
         SELECT ... FROM B  ┘
         → 코드에서 합침
```

#### 차이가 만드는 결과

|                                  | 순차형 (직렬)                       | 병렬형                                |
| -------------------------------- | ----------------------------------- | ------------------------------------- |
| **입구를 어디서**          | 벡터 결과의`chunk_id`             | 질문에서 뽑은**이름**           |
| **언제 출발**              | 벡터가 끝난 뒤                      | 동시에                                |
| **지연**                   | 줄줄이 이어져**느린 편**      | 겹쳐 돌아**빠른 편**            |
| **벡터가 헛짚으면**        | **그래프도 엉뚱한 데서 출발** | 영향 없음. 독립적으로 돈다            |
| **엔티티 추출이 실패하면** | 그런 단계가**아예 없다**      | **그래프 갈래가 통째로 죽는다** |
| **합칠 때 (3-4)**          | 독립이 아니라 RRF 못 씀 → 덧붙이기 | 독립이라**RRF 가능**            |

⚠️ **지연 비교는 경향이지 법칙이 아니다.** 병렬형도 엔티티 추출에 LLM을 쓰면 그만큼 시간이 들고, 순차형은 진입점이 좁아 트래버설이 오히려 짧게 끝날 수 있다.

#### 한 문장씩

- **순차형** — *"벡터가 찾은 조각에서 출발해 그 주변을 더 캐본다."* 그래프가 **벡터의 확장기**다.
- **병렬형** — *"벡터와 그래프에게 같은 질문을 각각 던지고 답을 모은다."* 그래프가 **또 하나의 검색기**다.

#### 가장 짧은 구분법 — 주어를 언제 뽑나

```
병렬형   주어를 지금 뽑는다      (질문에서, 질의 시점에)
순차형   주어를 이미 뽑아뒀다    (색인 때 뽑아둔 걸 chunk_id로 꺼냄)
```

순차형에서 진입 노드를 찾을 때는 **레코드의 `text`를 읽지 않는다.** `chunk_id`만 가지고 *"이 조각에서 추출된 노드가 뭐냐"*를 그래프DB에 물을 뿐이다 (text는 나중에 프롬프트에 실린다). **주어를 새로 뽑는 작업 자체가 없다.**

각자의 약점이 여기서 곧장 따라 나온다.

- **병렬형** — 지금 뽑으니 **뽑기에 실패할 수 있다.** 고유명사 없는 질문이면 못 뽑는다.
- **순차형** — 이미 뽑아둔 걸 꺼내니 뽑기 실패가 없다. 대신 **어느 조각을 꺼낼지가 벡터에 달려 있다.**

**서로의 약점을 맞바꾼 구조**라는 게 위 표의 결론이다. 그래프는 **노드 이름을 알아야 들어갈 수 있으므로**, `"휴가 관련 규정 알려줘"`처럼 고유명사가 없는 질문에서는 병렬형의 그래프 갈래가 출발조차 못 한다. 순차형은 질문에서 명사를 뽑을 필요가 없어 이 약점이 없다 — 대신 **벡터가 틀리면 같이 틀린다.**

어느 쪽이 표준인지는 정해져 있지 않다 ([rag-graphdb-hybrid-pipeline.md](../03-graphrag/rag-graphdb-hybrid-pipeline.md) 4장 Step 2). **아래 3-1부터는 병렬형 기준으로 이어간다.**

### 3-1. 질문 가공 — 두 DB가 알아듣는 말이 다르다

질문 B: `"2026년 개정에서 연차 조항이 바뀌었는데, 영향받는 다른 규정이 뭐가 있나?"`

**이 한국어 문장 자체로는 어느 DB도 받지 못한다.** 두 창고가 요구하는 입력 형태가 다르기 때문이다.

- **벡터DB** — 하는 일이 좌표 간 거리 계산이라 입력이 반드시 **숫자 배열**이어야 한다.
- **그래프DB** — 좌표 개념이 아예 없다. *"이 노드에서 시작해 엣지를 따라가라"*가 전부라 입력이 **노드를 지목하는 이름이나 ID**여야 한다.

**두 번 검색하려고 두 번 가공하는 게 아니라, 받는 쪽이 요구하는 형태가 달라서 두 번 번역하는 것**이다.

```
질문 (한국어 문장)
   ├─→ 벡터로 번역     [0.019, -0.171, ...]     ★ 색인 때 쓴 그 모델이어야 한다
   └─→ 엔티티로 번역   ["연차", "2026 개정"]
```

#### 엔티티 추출이 하는 일

**질문에서 "그래프의 노드가 될 만한 것"만 골라낸다.**

```
"2026년 개정에서 연차 조항이 바뀌었는데, 영향받는 다른 규정이 뭐가 있나?"

뽑는다:  "연차"       → 그래프에 (연차이월제도) 노드가 있다
        "2026 개정"  → 그래프에 (인사규정2026) 노드가 있다
버린다:  "바뀌었는데", "영향받는", "뭐가 있나"
        ↑ 그래프에 이런 이름의 노드는 없다
```

대표적인 방법 세 가지 — 사전 매칭(그래프 노드 이름 목록과 문자열 대조, 제일 쌈), NER 모델, LLM 호출(가장 유연). 실무에선 섞어 쓰기도 한다.

⚠️ **주어를 뽑는 건 그래프DB가 아니다.** 자주 뭉개지는 지점이라 컴포넌트를 갈라두자.

```
질문 "2026년 개정에서 연차 조항이..."
   │
   ▼ [엔티티 추출기]   ← 그래프DB 밖의 별개 컴포넌트 (사전/NER/LLM)
"연차", "2026 개정"
   │
   ▼ [그래프DB]        ← 이제서야 등장
"'연차'라는 이름의 노드 있나?" → (연차이월제도) → 트래버설
```

그래프DB가 하는 일은 **이름을 받아 노드를 찾고 관계를 따라가는 것**까지다. 문장에서 주어를 골라내는 일은 그 앞의 다른 놈이 한다 ([rag-overall-flow.md](../01-basics/rag-overall-flow.md) 3장 — 컴포넌트들은 서로를 모르고, 전부 내 스크립트가 순서대로 부른다).

★ **색인 때의 관계 추출(2-4)과 헷갈리기 쉽다.** 이름이 비슷하지만 다른 작업이다.

|         | 색인 때 (2-4)              | 질의 때 (3-1)                              |
| ------- | -------------------------- | ------------------------------------------ |
| 대상    | 조각**5만 개**       | 질문**한 줄**                        |
| 뽑는 것 | 노드**+ 엣지(관계)** | **노드 이름만**                      |
| 비용    | 이 아키텍처 최대 비용      | 무시할 수준                                |
| 목적    | 그래프를**만든다**   | 그래프를**어디서부터 읽을지** 정한다 |

질의 때 관계를 안 뽑는 이유는 간단하다 — **관계는 이미 그래프에 다 들어 있다.** 지금 필요한 건 그 망의 입구뿐이다.

#### ★ 이 두 갈래는 병렬형에만 있다

**순차형이면 엔티티 추출 단계가 아예 없다.** 벡터 검색 결과의 `chunk_id`가 진입점을 대신 찾아주기 때문이다 (2-5의 공통 키가 여기서 쓰인다). 두 형태의 전체 비교는 **3-0** 참고.

### 3-2. 벡터 검색

**입력** 질문 벡터 → **출력** 후보 조각 수십 개

코사인 유사도로 가까운 조각을 뽑는다. 실무에선 **키워드 검색(BM25)을 같이 돌린다** — `"제12조"`나 제품코드처럼 정확히 일치해야 하는 건 벡터가 약하기 때문이다 ([vector-db.md](../01-basics/vector-db.md) 5장).

질문 B에서 여기까지 나오는 것 — `제12조` 본문, "연차" 관련 문단들. **그런데 `퇴직정산규정 제4조`는 안 나온다.** 그 문서에는 "연차 개정"이라는 말이 안 적혀 있으니 의미가 안 가깝다.

### 3-3. 그래프 트래버설

**입력** 진입 노드 → **출력** 관계 경로

**진입점부터 어떻게 잡나 (순차형).** 여기서도 2-5의 공통 키를 쓴다.

```cypher
// 1. 벡터 검색 top-5의 chunk_id를 받아온다
// 2. 그 조각들에서 추출된 노드를 찾아 시작점으로 삼는다
MATCH (n)
WHERE any(cid IN n.source_chunk_id WHERE cid IN ['c12-03', 'c07-01', ...])
RETURN n
```

병렬형이면 이 대신 질문에서 뽑은 엔티티 이름으로 노드를 직접 찾는다. 어느 쪽이 표준인지는 정해져 있지 않다 ([rag-graphdb-hybrid-pipeline.md](../03-graphrag/rag-graphdb-hybrid-pipeline.md) 4장 Step 2).

진입점을 잡았으면 거기서 관계를 따라간다.

```
(연차이월제도) ─[정의됨]→ (제12조) ─[개정함]→ (제9조)
                              │
                              ├─[적용대상]→ (정규직)
                              └─[참조됨]→ (퇴직정산규정 제4조)   ← ★ 벡터가 못 찾은 것
```

두 다리 건너서 `퇴직정산규정 제4조`가 나온다. **연차 규정이 바뀌면 퇴직 정산이 영향받는다** — 두 문서 어디에도 같이 적혀 있지 않지만 관계를 따라가면 나온다. 이게 질문 B의 답이고, 그래프를 붙이는 유일한 이유다.

**벡터가 구조적으로 못 하는 두 가지.**

- **다단계 추적** — `A → B → C`를 못 따라간다. "질문과 얼마나 비슷한가"만 계산한다.
- **완전성** — top-k라 항상 "상위 몇 개"뿐이다. *"적용받는 규정을 전부"*를 보장할 수 없다. 트래버설은 조건에 맞는 걸 다 훑으므로 이게 가능하다.

⚠️ 대신 폭발 위험이 있다. `(인사규정2026)` 같은 허브 노드를 지나면 결과가 터진다. 홉 수·관계 타입·개수로 **3중 제동**을 건다 ([rag-graphdb-hybrid-pipeline.md](../03-graphrag/rag-graphdb-hybrid-pipeline.md) 5장).

### 3-4. 융합 (★ 이 노트의 핵심)

**"두 결과를 합친다"는 한마디로 넘어가는 곳인데, 여기가 하이브리드에서 유일하게 진짜 어려운 부분이다.** 섞는 것 자체는 쉽고, **섞을 수 있는 모양으로 만드는 게 대부분**이다.

#### 왜 그냥 못 합치나 — 자료형이 다르다

```
벡터DB 결과                            그래프DB 결과
[                                     [
  { chunk_id: "c12-03",                 { path: (제12조)-[참조됨]->(퇴직정산 제4조) },
    text: "제12조(연차휴가의 이월)...",    { path: (제12조)-[개정함]->(제9조) },
    score: 0.87 },                      ...
  ...                                 ]
]
                                      ← text가 없다
                                      ← score 체계가 없다 (또는 홉 수)
```

문제가 두 겹이다.

- **그래프 결과에는 원문 텍스트가 없다.** 노드는 `(퇴직정산 제4조)`라는 라벨만 들고 있지 그 조항의 문장을 모른다. 이대로는 LLM에 실을 수 없다.
- **점수를 비교할 수 없다.** 코사인 유사도 `0.87`과 "2홉 떨어짐"은 같은 자로 잰 값이 아니다.

#### 1단계 — 환원(hydration): 그래프 결과를 조각으로 되돌린다

2-5의 공통 키가 첫 번째 문제를 푼다.

```
(퇴직정산규정 제4조) 노드
        │
        │  노드에 심어둔 source_chunk_id = "c88-05"
        ▼
   벡터DB 조회:  chunk_id = 'c88-05' 인 레코드의 text
        │
        ▼
   { chunk_id: "c88-05", text: "제4조(퇴직 시 연차 정산) 미사용 연차는..." }
```

**이 순간 그래프 결과가 벡터 결과와 같은 자료형이 된다.** 둘 다 `chunk_id` 랭킹 리스트다. `source_chunk_id`를 심어두는 진짜 이유가 이거다 — 출처 기록용 메모가 아니라, **이게 없으면 그래프가 찾아낸 걸 프롬프트에 실을 방법이 아예 없다.**

#### 융합이 하는 일은 세 가지다

```
벡터DB 결과            그래프DB 결과
[조각 + 점수]          [노드·엣지 경로]
      │                     │
      └──────────┬──────────┘
                 ▼
          ① 형태 맞추기      ← 그래프 결과를 조각으로 환원 (위의 hydration)
          ② 순서 정하기      ← 어느 게 위로 갈지
          ③ 안 맞는 건 분리  ← 엣지는 따로 뺀다
                 ▼
        LLM에 넘길 최종 목록
```

★ **①과 ③은 병렬형이든 순차형이든 똑같고, 갈리는 건 ②뿐이다.**

#### ② 순서 정하기 — 병렬형: RRF가 성립한다

두 검색이 **서로를 모르고 독립적으로** 돌았다. 점수는 비교 불가이므로 **점수를 버리고 등수만 쓴다.**

```
RRF 점수 = Σ  1 / (k + 그 리스트에서의 등수)        (k는 관행적으로 60)
```

질문 B로 실제 계산해보면 이렇게 나온다.

| chunk                     | 벡터 등수     | 그래프 등수   | RRF 계산                      | 최종          |
| ------------------------- | ------------- | ------------- | ----------------------------- | ------------- |
| `c12-03` 제12조 본문    | **1위** | **2위** | 1/61 + 1/62 =**0.0325** | **1위** |
| `c88-05` 퇴직정산 제4조 | —            | **1위** | 1/61 =**0.0164**        | **2위** |
| `c07-01` 연차 일반 규정 | **2위** | —            | 1/62 =**0.0161**        | 3위           |
| `c41-01` 제9조 구규정   | —            | 3위           | 1/63 = 0.0159                 | 4위           |
| `c33-02` 휴가 신청 절차 | 3위           | —            | 1/63 = 0.0159                 | 5위           |

**여기서 두 가지를 읽어야 한다.**

- `c12-03`은 **양쪽에서 다 나와서** 압도적 1위가 된다. RRF의 본질이 이거다 — *"여러 검색기가 동의한 것을 위로 올린다."* 한쪽에서 1등이어도 다른 쪽에 없으면 양쪽 상위권을 이기지 못한다.
- `c88-05`는 **벡터에서 아예 안 나온 조각**인데 최종 2위로, 벡터 2위였던 `c07-01`을 제쳤다. **그래프를 붙인 효과가 정확히 이 한 줄이다.**

⚠️ **교집합이 아니라 합집합이다 (흔한 오해).** *"양쪽에서 겹치는 걸 찾아서 합친다"*로 이해하면 정반대가 된다.

```
벡터가 찾은 것:   c12-03, c07-01, c33-02
그래프가 찾은 것: c88-05, c12-03, c41-01

공통점만 취하면?  →  c12-03 하나만 남는다   ❌
실제로는?         →  다섯 개 전부 살린다     ✅
```

**겹침은 필터가 아니라 가산점**이다. 한쪽에만 있어도 탈락하지 않는다. 오히려 **한쪽에만 있는 게 값진 경우**가 있다 — `c88-05`는 벡터가 못 찾은 것이고, 그걸 살려주는 게 그래프를 붙인 이유 전체다. 공통점만 취하는 방식이었다면 얘가 제일 먼저 탈락한다.

정확히 말하면 **"둘을 다 모아놓고, 양쪽에 있는 것에 가산점을 줘서 순서를 정한다"**이다.

🏷️ `k=60`은 원 논문에서 제안된 값이 관행으로 굳은 것이고 **최적값 보장은 아니다** (논문 서지사항은 확인 안 됨). k가 크면 등수 차이의 영향이 완만해지고, 작으면 1등에 힘이 실린다.

#### ② 순서 정하기 — 순차형: RRF의 전제가 깨진다 (★)

**RRF의 힘은 "독립적인 검색기들이 동의했다"는 데서 나온다.** 순차형은 그 전제를 만족하지 않는다. 그래프가 벡터 결과에서 출발했기 때문이다.

```
벡터 랭킹:    1. c12-03    2. c07-01    3. c33-02
                  │
                  └─→ 이걸 진입점으로 그래프 트래버설
                          │
그래프 결과:  c12-03(진입점 자신), c88-05, c41-01
              ↑ 여기 c12-03이 나오는 건 당연하다. 거기서 출발했으니까
```

**여기서 RRF를 돌리면 `c12-03`이 두 표를 받는데, 두 번째 표에는 정보가 없다.** 자기가 출발점이었다는 사실을 자기 점수로 되돌려받는 **자기 투표**다. 벡터가 1등으로 뽑았다는 이유만으로 한 번 더 가산되어 **순위가 부풀려진다.**

그래서 순차형의 융합은 **합치는 것이 아니라 붙이는 것**에 가깝다.

```
벡터 랭킹을 뼈대로 두고
      └─→ 그래프가 새로 발견한 것(c88-05, c41-01)만 골라 덧붙인다
          (진입점으로 쓴 조각은 중복이므로 제외)
```

🏷️ **구체적 가중 방식은 구현마다 다르고 어느 쪽이 정답이라 단정할 근거는 없다.** 확실한 것은 **RRF가 검색기의 독립성을 전제한다**는 것, 그리고 순차형이 그 전제를 만족하지 않는다는 것뿐이다.

**두 구조의 성격 차이가 여기서 드러난다.**

|                  | 그래프의 역할               | 융합 방식                   | 대표 실패                                               |
| ---------------- | --------------------------- | --------------------------- | ------------------------------------------------------- |
| **병렬형** | 또 하나의**검색기**   | RRF (투표)                  | 엔티티 추출이 틀리면 그래프가 통째로 헛돈다             |
| **순차형** | 벡터 결과의**확장기** | 신규 발견분 덧붙이기 (보강) | 벡터가 엉뚱한 조각을 물면 그래프도 엉뚱한 데서 출발한다 |

#### ③ 다 환원되지는 않는다 (★)

**관계 그 자체는 어느 조각 하나에도 안 적혀 있을 수 있다.**

```
(제12조) -[참조됨]-> (퇴직정산 제4조)
```

이 엣지는 `c12-03`에서 뽑힌 게 아니라, **퇴직정산규정 쪽 조각(`c88-05`)의 "제12조를 준용한다"는 문장**에서 뽑혔을 수 있다. 즉 이 관계는 **두 조각에 걸친 정보**라 조각 하나로 환원되지 않는다.

그래서 실제로는 **두 트랙으로 갈라져 프롬프트에 들어간다.**

```
그래프 결과
   ├─ 노드 → chunk_id로 환원 가능 ──→ 벡터 결과와 RRF 융합 ──→ [문서 발췌]
   └─ 엣지(관계) 자체 ─────────────→ 문장으로 직렬화 ────────→ [관계 정보]
```

**엣지는 순위를 매기지 않는다.** 랭킹 경쟁에 참여하지 않고 별도 섹션으로 그냥 붙는다. **융합되는 건 절반이고 나머지 절반은 따로 간다** — 3-6 프롬프트에 `[문서 발췌]`와 `[관계 정보]`가 나란히 있는 게 이 구조의 결과물이다.

🏷️ 이건 **설계 판단이고 구현마다 다르다.** 관계를 텍스트로 만들어 아예 하나의 랭킹에 밀어넣는 구성도 가능하다.

### 3-5. 리랭킹

**입력** 후보 수십 개 → **출력** 5~10개

여기가 왜 별도 단계인지는 **채점 방식의 차이**에 있다.

|           | 벡터 검색                                      | 리랭커                                                   |
| --------- | ---------------------------------------------- | -------------------------------------------------------- |
| 방식      | 질문과 조각을**따로** 벡터화해 거리 측정 | 질문과 조각을**한 쌍으로 묶어** 모델에 통째로 투입 |
| 사전 계산 | 조각 벡터는 미리 계산됨                        | **불가능.** 질문이 와야 계산 시작                  |
| 속도      | 매우 빠름                                      | 느림 (후보 하나마다 모델 1회)                            |
| 정확도    | 거칠다                                         | 정확하다                                                 |

**그래서 순서가 이렇게 나온다** — 빠른 걸로 수만 개에서 수십 개로 좁히고, 느린 걸로 최종 몇 개를 고른다. 처음부터 리랭커로 5만 개를 채점할 수는 없다.

### 3-6. 프롬프트 조립 — 관계를 텍스트로 직렬화 (★)

**LLM은 그래프를 못 먹는다.** 노드와 엣지를 그대로 던질 수 없으니 **문장으로 풀어써야 한다.** 자주 빠뜨리는 단계다.

```
[시스템] 아래 자료만 근거로 답하라. 자료에 없으면 "모른다"고 답하라. 근거 조항을 표시하라.

[문서 발췌]                        ← 벡터DB 산출물: 원문 그대로
제12조(연차휴가의 이월) 미사용 연차는 익년 3월 31일까지 이월한다...

[관계 정보]                        ← 그래프DB 산출물: 직렬화한 것
- 인사규정2026 제12조는 인사규정2023 제9조를 개정했다
- 제12조는 정규직에만 적용된다
- 퇴직정산규정 제4조가 제12조를 참조한다

[질문] 2026년 개정에서 연차 조항이 바뀌었는데, 영향받는 다른 규정이 뭐가 있나?
```

**두 창고가 서로 다른 성격의 재료를 댄다.** 벡터는 *"뭐라고 쓰여 있나"*(근거 문장), 그래프는 *"뭐와 얽혀 있나"*(구조). LLM은 이 둘을 합쳐 답을 쓴다.

`"자료에 없으면 모른다고 하라"`는 지시가 형식적으로 보이지만 **환각을 막는 실질 장치**다. 검색이 실패했을 때 LLM이 아는 척하는 걸 여기서 막는다.

---

## 4. 흔한 오해 — 그래프는 질의 시점에 만들어지지 않는다 (★)

> *"벡터DB가 결과를 주면, 그걸 보고 그래프DB가 결과를 만들어서 저장한다"* — **틀렸다.**

**그래프는 오프라인에 이미 완성돼 있다.** 질의 시점에 그래프DB가 하는 일은 **읽기(트래버설)뿐**이고, 쓰기는 없다.

순차형에서 벡터 결과의 역할은 딱 하나 — **이미 존재하는 그래프의 어느 노드부터 읽기 시작할지 진입점을 찍어주는 것**이다.

**질의 시점에 그래프를 만든다면 무슨 일이 생기나.**

- **응답 시간** — 조각마다 LLM을 태워야 하니 질문 하나에 수 초에서 수십 초. 검색 경로는 수백 ms 예산이다.
- **중복 증식** — 같은 질문을 두 번 하면 같은 노드가 두 번 생긴다.
- **동시성** — 여러 요청이 같은 노드를 동시에 쓰려 든다.

요컨대 **읽기 경로에 쓰기를 섞은 것**이다. 백엔드로 옮기면 자명하다 — **조회 API 안에서 `CREATE INDEX`를 돌리지 않는다.** 인덱스는 미리 만들고 조회는 읽기만 한다.

⚠️ **예외는 있다.** 문서 갱신을 감지해 백그라운드로 증분 반영하거나, 트래버설 결과를 캐싱하는 설계는 존재한다. 다만 그건 **최적화이지 기본 구조가 아니고**, 그 경우에도 "검색 결과를 그래프로 저장"하는 것은 아니다.

## 5. 단계별 산출물 한눈에

| 단계         | 시점     | 입력         | 출력              | 실행 주체     |
| ------------ | -------- | ------------ | ----------------- | ------------- |
| 파싱         | 오프라인 | PDF 바이너리 | 텍스트 + 구조     | 파서          |
| 청킹         | 오프라인 | 문서 텍스트  | 조각 + 메타데이터 | 내 스크립트   |
| 임베딩       | 오프라인 | 조각 텍스트  | 실수 배열         | 임베딩 모델   |
| 벡터 색인    | 오프라인 | 벡터 + 원문  | ANN 인덱스        | 벡터DB        |
| 관계 추출    | 오프라인 | 조각 텍스트  | 노드 / 엣지       | **LLM** |
| 그래프 적재  | 오프라인 | 노드 / 엣지  | 그래프            | 그래프DB      |
| ───       | ───   | ───       | ───            | ───        |
| 질문 임베딩  | 온라인   | 질문 문장    | 실수 배열         | 임베딩 모델   |
| 벡터 검색    | 온라인   | 질문 벡터    | 후보 조각         | 벡터DB        |
| 트래버설     | 온라인   | 진입 노드    | 관계 경로         | 그래프DB      |
| 융합         | 온라인   | 두 결과 집합 | 통합 후보         | 내 스크립트   |
| 리랭킹       | 온라인   | 후보 수십 개 | 5~10개            | 리랭커 모델   |
| 조립·직렬화 | 온라인   | 조각 + 관계  | 프롬프트 텍스트   | 내 스크립트   |
| 생성         | 온라인   | 프롬프트     | 답변              | **LLM** |

**LLM이 등장하는 곳이 두 군데뿐**이고, 그 둘의 성격이 완전히 다르다는 게 이 표의 핵심이다. 오프라인의 LLM은 **비용을 만들고**, 온라인의 LLM은 **지연을 만든다.**

---

📌 **핵심 요약**
하이브리드 RAG는 같은 원본을 **두 번 가공해 두 창고에 넣는 구조**다. 벡터DB는 "이 문단이 무슨 뜻인가", 그래프DB는 "이것과 저것이 어떻게 얽혔나"를 저장하고, 둘은 **색인 때 심어둔 공통 키(`source_chunk_id`)**로 이어진다. 이 키가 진입점 찾기·텍스트 환원·융합 기준 **세 군데**에서 쓰이므로, 색인 때 안 심으면 하이브리드 자체가 성립하지 않는다. 융합은 한 번에 되는 게 아니라 **(1) 그래프 결과를 조각으로 환원해 자료형을 맞추고 (2) 점수를 버리고 등수로 합치는(RRF)** 두 단계이며, 조각으로 환원되지 않는 **관계 자체는 별도 트랙으로 직렬화되어** 프롬프트의 다른 섹션에 실린다. 가장 흔한 오해는 그래프가 질의 시점에 만들어진다고 보는 것인데, 그래프는 **오프라인에 완성돼 있고 질의 때는 읽기만 한다.**

🔗 **참고 자료**

- Neo4j 공식 문서 — 그래프 데이터 모델과 Cypher 트래버설 (1차 자료)
- Microsoft Research의 **GraphRAG** — 이 구조의 대표 사례 (**존재는 거의 확실, 정확한 URL과 벤치마크 수치는 확인 안 됨**)

🌱 **심화 키워드**

- **Entity Resolution** — 추출된 `"제12조"`와 `"인사규정 12조"`가 같은 노드인지 판정하는 문제. 실패하면 그래프가 조각조각 끊긴다.
- **RRF (Reciprocal Rank Fusion)** — 점수 스케일이 다른 검색 결과를 **등수만으로** 합치는 기법. 3-4의 실체.
- **Bi-encoder vs Cross-encoder** — 3-5 표의 두 열에 붙는 정식 이름. 왜 검색과 리랭킹이 분리되는지의 근거.
- **Multi-hop QA** — 다단계 추론이 필요한 질문 유형. 그래프 도입의 근거가 되는 질문군.

❓ **남은 질문**

- 관계 추출에 LLM을 쓴다는 건 **추출 자체가 틀릴 수 있다**는 뜻이다. `(제12조)-[개정함]->(제20조)`처럼 잘못 저장되면 이 오류는 어느 단계에서 잡히나? 벡터DB의 오류(엉뚱한 조각이 걸림)는 리랭커가 걸러주지만, 그래프의 **거짓 엣지**는 걸러줄 장치가 파이프라인 어디에도 없어 보인다.
- 벡터DB는 조각을 지우면 끝인데, 그래프DB에서 문서 하나를 삭제하면 무슨 일이 생기나? `source_chunk_id`가 그 문서인 엣지만 지우면 되나 — 여러 문서에서 함께 추출된 노드는?
- 2-5의 공통 키 방식과 엔티티 이름 매칭 방식은 각각 어디서 깨지나?
