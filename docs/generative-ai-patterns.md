# 생성형 AI 설계 패턴, 무엇을 골라 넣었나

두 번째 참고 도서(*생성형 AI 설계 패턴*)는 패턴 32개를 다룹니다.
전부 억지로 구현하지는 않았습니다. 이 문서는 **무엇을 골랐고, 부분 적용한 경계는 어디이며, 넘긴 것은 왜 넘겼는지**를 남긴 기록입니다.
중간에 판단이 바뀐 것도 두 개 있어서 그 과정까지 함께 적었습니다.

패턴 목록 자체보다 이 판단 기준이 더 오래 쓸모 있을 거라고 봤습니다.

## 이 문서를 읽는 순서

이 문서는 생성형 AI를 처음 배우는 입문서가 아니라, 기본 RAG를 실행한 뒤 설계를 되돌아보는 문서입니다. [RAG 학습 가이드](README.md)의 5단계까지 마친 다음 읽는 것을 권장합니다.

처음부터 32개 이름을 외우지 말고 다음 순서로 묶어 봅니다.

1. **지식을 넣는다:** 기본 RAG, 의미 기반 색인화, 대규모 색인화
2. **검색 결과를 다듬는다:** 색인 인식 검색, 노드 후처리, 심층 탐색
3. **답을 검사한다:** 신뢰할 수 있는 생성, 심판형 LLM, 성찰, 자체점검
4. **서비스 경계를 만든다:** 의존성 주입, 장기 기억, 가드레일
5. **필요할 때만 에이전트로 확장한다:** 도구 호출과 에이전트형 작업흐름

각 패턴에서는 “무슨 기법인가?”보다 다음 세 가지를 먼저 묻습니다.

- 이 패턴이 없을 때 현재 코드에서 실제로 어떤 실패가 발생하는가?
- 추가되는 모델 호출·지연시간·운영 복잡성은 얼마인가?
- 효과를 어떤 테스트나 지표로 확인할 것인가?

이 세 질문에 답하지 못하면 패턴을 추가할 시점이 아닐 가능성이 큽니다.

## 32개 패턴 반영 지도

`구현`은 독립 코드와 실행 경로가 있고, `부분`은 더 작은 형태나 수동 방식만 적용했다는 뜻입니다.

| 장·패턴 | 상태 | 이 저장소에서의 대응 |
|---|---|---|
| 2.1 로짓 마스킹 | 미구현 | 모델 런타임 내부 기능이며 직접 로짓에 접근하지 않음 |
| 2.2 문법 | 구현 | `structured.ts`의 JSON 스키마 출력 |
| 2.3 스타일 전이 | 미구현 | 검색 품질과 독립적이라 제외 |
| 2.4 역중립화 | 미구현 | 페르소나·관점 제어를 제품 요구로 두지 않음 |
| 2.5 콘텐츠 최적화 | 부분 | 질의 재작성은 하지만 마케팅/매체별 콘텐츠 최적화는 하지 않음 |
| 3.1 기본 RAG | 구현 | `rag.ts`의 검색→컨텍스트→생성 |
| 3.2 의미 기반 색인화 | 구현 | 청킹, Ollama 임베딩, Chroma/SQLite 저장 |
| 3.3 대규모 색인화 | 구현 | 제한된 크기의 배치 처리와 증분 인덱싱 |
| 4.1 색인 인식 검색 | 구현 | Self-Query 메타데이터 필터와 질의 라우팅 |
| 4.2 노드 후처리 | 구현 | 크로스 인코더 재랭킹, Parent-Child 복원 |
| 4.3 신뢰할 수 있는 생성 | 구현 | 출처 번호 강제와 코드 기반 인용 검사 |
| 4.4 심층 탐색 | 구현 | Multi-Query, HyDE, GraphRAG 확장 |
| 5.2 사고 연쇄 | 문서만 | 내부 추론 노출 대신 근거 기반 답변을 우선 |
| 5.3 사고 트리 | 문서만 | 호출 비용과 평가 복잡성 때문에 제외 |
| 5.4 어댑터 조정 | 문서만 | 학습 데이터·GPU·평가가 필요한 별도 프로젝트 |
| 5.5 지시사항 진화 | 미구현 | 합성 지시 데이터 생성·선별 루프 없음 |
| 6.1 심판형 LLM | 구현 | `eval/judge.ts`와 답변 평가 스크립트 |
| 6.2 성찰 | 부분 | 인용 자체점검 실패 시 1회 제한 재작성 |
| 6.3 의존성 주입 | 구현 | `RagDependencies`, `ConversationStorePort` |
| 6.4 프롬프트 최적화 | 부분 | 프롬프트를 역할별로 분리했지만 자동 탐색은 없음 |
| 7.1 도구 호출 | 부분 | 도구 선택 라우터는 있으나 모델 네이티브 호출 루프는 없음 |
| 7.2 코드 실행 | 미구현 | 사용자 생성 코드를 실행하는 샌드박스 없음 |
| 7.3 다중 에이전트 협업 | 미구현 | 현재 문제 규모에서 조정 비용이 이득보다 큼 |
| 8.1 소규모 언어 모델 | 부분 | 로컬 Ollama 모델 교체 가능, 별도 품질 비교 없음 |
| 8.2 프롬프트 캐싱 | 미구현 | 응답 신선도·세션 격리 정책부터 정해야 함 |
| 8.3 인퍼런스 최적화 | 부분 | 임베딩 배치·타임아웃은 있으나 양자화/서빙 최적화 없음 |
| 8.4 성능 저하 테스트 | 부분 | Recall/MRR·지연 측정은 있으나 고정 기준선 CI 게이트 없음 |
| 8.5 장기 기억 | 구현 | API 세션을 SQLite에 영속화하고 최근 턴만 조회 |
| 9.1 템플릿 생성 | 부분 | RAG 메시지 조립 함수는 있으나 범용 템플릿 엔진은 없음 |
| 9.2 조립 후 재구성 | 부분 | 검색 문서를 조립해 생성하지만 별도 재구성 단계는 없음 |
| 9.3 자체점검 | 구현 | `answerQuestionReliably`의 인용 검사와 제한 재시도 |
| 9.4 가드레일 | 구현 | HTTP 경계의 입력 검사와 출력 PII 마스킹 |
| 10.1 에이전트형 작업흐름 | 부분 | vector/graph/none 라우팅까지만 의도적으로 제한 |

1장의 기초 모델, 컨텍스트 내 학습, 사후훈련은 개별 패턴이 아니라 위 선택을 이해하는 배경 개념이다. 이 저장소는 기초 모델을 Ollama로 호출하고 프롬프트·검색 문서를 컨텍스트에 넣지만, 모델 가중치를 바꾸는 사후훈련은 하지 않는다.

## 판단 기준

기준은 하나였습니다.

> **그 패턴이 고치는 문제가 이 저장소에서 실제로 관찰되는가.**

"좋은 패턴인가"가 아닙니다. 좋은 패턴이라도 여기에 그 문제가 없으면
코드만 늘고 배우는 것은 없습니다. 반대로 화려하지 않아도 실제로 겪고 있는 문제라면
고치는 과정에서 원리를 손으로 익히게 됩니다.

지금 공부 목표가 RAG, 벡터DB, LLM 위키 파이프라인이라는 점도 함께 걸었습니다.

## 채택한 패턴

| 패턴 | 여기서 실제로 관찰된 문제 | 관련 위치 |
|:---|:---|:---|
| **패턴 2 구조화 출력** | Self-Query 필터 추출이 프롬프트로 "JSON으로 답해"라고 부탁만 하고 있었다. 모델이 설명 문장을 앞에 붙이거나 코드 펜스로 감싸면 파싱이 깨졌다 | `src/lib/structured.ts` |
| **패턴 11 신뢰할 수 있는 생성** | 답변이 자료에 없는 내용을 섞어도 알아챌 방법이 없었다. `[자료 n]` 표기를 요구하고 번호 존재 여부를 코드로 검사한다 | `src/lib/citations.ts` |
| **패턴 17 심판형 LLM** | 평가가 검색만 재고 있었다. Recall/MRR은 만점인데 답이 틀린 경우를 못 잡는다 | `src/lib/eval/judge.ts`, `npm run eval:answer` |
| **패턴 8 대규모 색인화** | 임베딩 요청에 **크기 상한이 없었다.** 청크 수천 개가 요청 하나로 나가면 제한 시간에 걸려 통째로 실패한다 | `src/lib/batch.ts` |
| **패턴 9 색인 인식 검색** | 자연어 안의 정형 조건을 벡터에 섞어 검색하고 있었다. Self-Query로 의미 질의와 metadata 필터를 분리한다 | `src/lib/search/self-query.ts` |
| **패턴 10 노드 후처리** | 빠른 1차 검색의 순위만 믿으면 오탐이 남는다. 후보만 크로스 인코더로 다시 정렬한다 | `src/lib/search/rerank.ts` |
| **패턴 12 심층 탐색** | 표현 하나로 검색하면 관련 문서를 놓쳤다. Multi-Query·HyDE·그래프 확장으로 탐색 폭을 넓힌다 | `src/lib/search/rewrite.ts`, `src/lib/search/graph-rag.ts` |
| **패턴 18·31 성찰·자체점검** | 인용 검사는 경고만 만들고 답을 고치지 않았다. 실패 시 피드백을 넣어 최대 한 번 재작성한다 | `src/lib/rag.ts`의 `answerQuestionReliably` |
| **패턴 19 의존성 주입** | 전역 DB·LLM에 묶이면 실패 경로를 테스트하기 어렵다. 검색기와 생성기를 주입할 수 있게 했다 | `RagDependencies`, `ConversationStorePort` |
| **패턴 28 장기 기억** | 인메모리 세션은 서버 재시작 때 사라졌다. API 대화를 SQLite에 저장한다 | `src/sqlite/conversation-store.ts` |
| **패턴 32 가드레일** | 신뢰할 수 없는 입력이 그대로 프롬프트에 들어갔고, 적재 문서에 개인정보가 섞이면 답변으로 새어 나갈 경로가 있었다 | `src/lib/guardrails.ts` |
| **에이전트형 작업흐름(부분)** | 인사에까지 벡터 검색이 한 번 돌았다. 관련 없는 청크가 컨텍스트에 들어가 답을 오히려 흐린다 | `src/lib/router.ts`, `npm run route` |

패턴 11과 17을 한 쌍으로 넣은 이유는 **검사 비용이 다르기 때문**입니다.
인용 번호 검사는 정규식 한 줄이라 공짜고, 심판 채점은 답변마다 LLM 호출이 한 번 더 듭니다.
값싼 검사를 먼저 걸어 걸러낸 뒤 비싼 검사를 돌리는 순서가 그대로 코드에 남아 있습니다.

패턴 8은 처음에 "배치 임베딩이 없다"고 진단했다가 코드를 읽고 고쳤습니다.
`OllamaEmbeddingFunction.generate(texts)`는 이미 배열을 통째로 한 요청에 보내고 있었습니다.
**구멍은 배치가 없는 것이 아니라 상한이 없는 것**이었습니다. 진단이 한 단계 어긋나면
엉뚱한 것을 만들게 되므로, 패턴 이름만 보고 코드를 짐작하지 않는 편이 좋습니다.

## 처음엔 넘겼다가 되돌아온 둘

에이전트와 가드레일은 처음에 "지금은 아니다"로 분류했다가 다시 가져왔다.
넘긴 이유와 되돌아온 이유를 같이 적어둔다. 판단이 바뀌는 과정 자체가 남을 만하다.

### 에이전트형 작업흐름 -> 질의 라우팅만

**처음 판단:** 도구를 여러 개 쥐여주고 모델이 스스로 계획을 세우게 하면
답이 틀렸을 때 검색 탓인지, 도구 선택 탓인지, 계획 탓인지 분리가 안 된다.
기반이 흔들리는 상태에서 얹으면 디버깅이 불가능해진다.

**되돌아온 이유:** 전부가 아니라 **한 단계만** 떼어내면 그 문제가 사라진다.
도구를 고르는 것까지만 모델에게 맡기고 실행은 코드가 하면,
틀렸을 때 어디서 틀렸는지가 로그 한 줄로 보인다.
그리고 그 한 단계만으로도 에이전트의 핵심 어려움
(**선택이 틀리면 그 뒤가 전부 틀린다**)은 그대로 체험된다.

덤으로 실제 문제 하나가 고쳐졌다. 지금까지 "안녕하세요"에도 벡터 검색이 돌고 있었다.
**검색을 건너뛰는 것도 선택지**라는 관점은 라우터를 만들기 전에는 아예 없었다.

다단계 계획과 모델 네이티브 도구 호출 루프는 여전히 넘긴다. 자기 검증은 범위를 좁혀
**인용 형식 실패를 감지하고 한 번만 다시 쓰는 형태**로 추가했다. 종료 조건이 명확해
무한 루프 없이 효과와 비용을 관찰할 수 있기 때문이다.

### 가드레일 -> 경계에만

**처음 판단:** 로컬에서 혼자 돌리는 학습용이고 데이터도 위키백과와 커피 원두 샘플이다.
막을 위협이 실재하지 않으니 코드만 늘고 배우는 것은 없다.

**되돌아온 이유:** 위협이 없어도 **어디에 두는가**를 손으로 정해보는 값이 있다.
가드레일을 RAG 로직 안에 흩어놓으면 검사가 두 번 돌거나 한 번도 안 돈다.
경계(HTTP 라우트)에 모아두면 "신뢰할 수 없는 입력이 들어오는 문"과
"결과가 나가는 문"이 코드에서 한눈에 보인다. 그 배치 감각이 학습 대상이다.

그리고 정규식 인젝션 검사가 **얼마나 쉽게 뚫리는지** 직접 만들어봐야 안다.
띄어쓰기를 바꾸거나 다른 언어로 쓰면 그냥 통과한다.
"가드레일을 붙였으니 안전하다"는 착각을 깨는 게 오히려 실전에 가깝다.

## 문서로만 남기는 것

아래는 구현하지 않는다. 이 저장소의 흐름에서 벗어나거나,
넣어도 효과를 관찰할 수 없어서다. **개념만 알아두고 넘어간다.**

### 어댑터 / 파인튜닝 (LoRA, QLoRA 등)

모델 가중치를 도메인에 맞게 손보는 쪽이다.

알아둘 것은 **RAG 와 파인튜닝이 서로 다른 문제를 푼다**는 점이다.
흔히 "둘 중 뭐가 낫냐"로 묻지만 그 질문 자체가 잘못됐다.

| | RAG | 파인튜닝 |
|:---|:---|:---|
| 푸는 문제 | 모델이 **모르는 사실**을 준다 | 모델이 **못 하는 형식/말투/작업**을 가르친다 |
| 지식 갱신 | 문서만 다시 넣으면 즉시 반영 | 다시 학습해야 반영 |
| 근거 제시 | 출처를 그대로 보여줄 수 있다 | 어디서 나온 답인지 알 수 없다 |
| 드는 것 | 벡터DB 운영 | 학습 데이터, GPU, 평가 루프 |

사내 규정 최신본을 답하게 하려면 RAG 다. 아무리 파인튜닝해도 규정이 바뀌면 끝이다.
반대로 "항상 이 회사 문체로 보고서 형식으로 써라"는 RAG 로 안 된다.
프롬프트로 매번 지시할 수는 있지만 길어지고 흔들린다.

**구현하지 않는 이유:** 학습 데이터 수집, GPU, 평가 루프까지 딸린 완전히 다른 프로젝트다.
그 사이 벡터DB 공부는 한 발짝도 나가지 않는다.
순서로도 뒤다 - RAG 로 안 되는 것이 무엇인지 먼저 확인해야
"왜 파인튜닝했는지" 설명할 근거가 생긴다.

### 사고 연쇄 / 사고 나무 (CoT / ToT)

답하기 전에 추론 과정을 길게 쓰게 만드는 기법이다.
수학이나 다단계 논리 문제에서 정확도를 올린다.

그런데 RAG 의 생성 단계는 성격이 다르다. 과제가
**주어진 자료에서 답을 찾아 옮겨 적기**라서, 추론을 길게 시킬수록
자료를 벗어나 지어낼 여지가 늘어난다. 근거성(groundedness)과 방향이 상충한다.

ToT 는 후보를 여러 갈래로 펼쳤다 고르므로 LLM 호출이 몇 배가 된다.
로컬 Ollama 한 대로는 이득 대비 대기시간이 감당되지 않는다.

> **다만 RAG 에 맞는 변형은 있다.** "먼저 자료에서 근거 문장만 뽑고, 그 문장들로만 답한다"는
> 두 단계 방식이다. 추론을 늘리는 게 아니라 **근거를 좁히는** 쪽이라 근거성과 방향이 같다.
> 지금은 인용 검증(패턴 11)과 심판형 LLM(패턴 17)이 같은 문제를 다른 각도에서 잡고 있어
> 중복이라 넣지 않았다. 근거성 점수가 안 오르는 게 확인되면 그때 볼 카드다.

### 스타일 제어 (2장 대부분)

말투, 페르소나, 출력 길이, 톤을 프롬프트로 잡는 기법이다.
제품에서는 중요하지만 RAG 관점에서 배울 것이 없다.
답변이 존댓말이든 반말이든 **검색이 맞는 청크를 가져왔는가**는 변하지 않는다.

이미 시스템 프롬프트에 "두세 문장, 한국어"를 지시하고 있고 그것이 사실상 전부다.
더 파봐야 프롬프트 문구만 길어진다.

같은 2장에서 패턴 2(구조화 출력)만 가져온 것은, 그것이 스타일이 아니라
**결과를 코드가 파싱할 수 있는가**라는 배관 문제이기 때문이다.
스타일은 사람이 읽고 판단하지만, 형식은 코드가 깨지느냐 마느냐가 걸린다.

## 다시 볼 조건

문서로만 남긴 것들도 조건이 바뀌면 값이 생긴다. 무엇이 바뀌면 다시 볼지 적어둔다.

- **CoT 변형(근거 추출 후 답변)** - 심판형 LLM 의 근거성 평균이 낮게 굳으면.
  지금 만든 `npm run eval:answer` 가 그 신호를 준다
- **다단계 에이전트** - 라우팅 정확도가 안정되고, 평가로 전략 변경 효과를 잴 수 있게 되면
- **파인튜닝** - RAG 로 안 되는 것이 무엇인지 먼저 확인한 뒤. 순서를 뒤집으면
  "왜 파인튜닝했는지" 설명할 근거가 없다
- **스타일 제어** - 이 코드가 남에게 보여줄 결과물을 내게 될 때
